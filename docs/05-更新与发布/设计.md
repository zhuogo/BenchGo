# 更新与发布设计

本板块负责应用、插件与移动端的打包、签名、分发、安装迁移、更新和回滚。总体关系见[总架构](../总架构.html)，源码装配见[工作台与 Agent](../02-工作台与Agent/设计.md)。不在本文维护逐版本流水账，当前版本以 manifest、引擎 pin 和实际发行产物为准。

## 1. 交付单元与版本来源

| 单元 | 版本与内容 | 更新边界 |
| --- | --- | --- |
| 桌面应用 | 根 `package.json`；Electron、官方 Harness、启动/托盘/安装器和离线插件种子 | 壳层、引擎、原生能力、安装器变更需要应用安装包 |
| `benchgo-plugin` | `plugins/benchgo/package.json`；五源码包业务与统一客户端 | 主机页面、工具集成、SuperAgent、Voice、Link 主机端随插件更新 |
| Android | `plugins/link/mobile/android/app/build.gradle`；`versionName` 对齐应用，`versionCode` 递增 | 原生能力、壳层和 APK 内置连接页面需更新 APK |
| 服务器工作台/中继 | 各自 CLI 和服务生命周期 | 两者不互相隐式安装，见[设备连接](../01-设备与远程连接/设计.md) |

应用与插件独立比较、独立递增。只改插件无需重编安装包；手机访问主机提供的页面时，升级的是当前连接主机，重启后重连/刷新即可，不能把主机插件提示当成 APK 更新。

官方引擎以 `upstream.json` 和 `deepseek-harness/` 子模块 pin 为真源。升级从官方 `origin/master` 获取提交，同步两处并重验兼容；不改官方源码，不恢复社区 Stable/Beta/Next 或 runtime patches。

## 2. 一个插件、五个入口

源码为 `plugins/benchgo`、`plugins/harness`、`plugins/superagent`、`plugins/voice`、`plugins/link`，最终只安装和更新一个 `benchgo-plugin`。

```text
benchgo-plugin                    基础层与统一客户端
benchgo-plugin/harness-plugin     Harness 聚合
benchgo-plugin/superagent-plugin  SuperAgent
benchgo-plugin/voice-plugin       Voice
benchgo-plugin/link-plugin        Link
```

- 基础层保留完整包根入口，供官方 `clientModules` 发现客户端；注册 ID 必须是 `benchgo-plugin`。
- Harness、SuperAgent、Voice 发布源码与动态资源生成到 `lib/modules/`；公共实现留包根，Link 使用既有服务和网页产物。
- 生成目录不手工维护；发布包不依赖源码同级目录，不携带旧业务副本、`.bak*` 或补丁临时文件。
- 检查五入口、runtime、资源导入和客户端发现；后端入口可解析不能替代客户端加载验证。
- 官方共享服务须保持宿主模块/作用域身份；版本相同或链接目标看似相同，不足以证明运行时单实例。

## 3. 构建与开发加载

根 `npm run setup/build/dev/start/check` 包装官方脚本，依赖由子模块锁定的 Corepack pnpm 管理。Windows 预览经 `scripts/desktop/prepare-dev.mjs` 启动已打包 BenchGo，不启动官方 Desktop。

BenchGo/Link 网页变更后运行 `npm run reload:plus`，重建业务模块、`lib/client.js`、Link 网页等；Harness 热加载后浏览器刷新。不构建服务器种子、不因此重启 Web，也不等于正式发行验收。

正式打包须从当前源码重建，记录构建提交并核对安装后的实际源码、客户端、插件与引擎。`npm run check` 只查版本、工作区和入口一致性，不代替构建或运行验证。

## 4. 品牌与平台身份

应用、插件和移动端均名 BenchGo，Windows 主程序为 `BenchGo.exe`。保留既有 applicationId、appId、协议、用户数据目录，确保原位升级与数据连续。

图标唯一来源为 `assets/brand/benchgo-app.svg`（带背景）和 `assets/brand/benchgo-mark.svg`（透明），是同一形象。窗口、托盘、安装/卸载、启动初始化、Android、网页 favicon、五入口统一复用；供应商品牌与第三方版权保留原归属。

Windows “应用”菜单顺序：关于 BenchGo、管理 dsh 命令、重启、退出。关于窗口使用 BenchGo 品牌和 `https://benchgo.cn`，引擎归属为补充。更新在 BenchGo 面板，不恢复原生“检查更新”菜单；重启走安全流程，失败明确返回，不静默退出。

## 5. 更新入口与状态

侧栏更新入口提供插件更新与桌面应用检查，读取当前连接主机状态。

- 当前版本已知且验签清单版本严格更高，才提示对应组件有更新。
- 未检查、检查失败、版本未知、已最新、已准备待重启分别显示；未知不能显示已最新。
- 红点只代表确认的新版本或待重启插件；加载新版本后清除，不重复安装待生效版本。
- 服务器显示由服务器部署管理，不要求安装 Windows EXE；清单 404 是通道未就绪，签名/权限/包下载失败仍按错误处理。
- 默认源为 `https://ghfast.top/`，可选 GitHub 直连或自定义 HTTPS 镜像；失败保留选择，不静默换源。
- 桌面检查通过官方 Desktop bridge；原生自动更新使用 BenchGo 配置的内置源，面板签名安装包链接遵循所选来源。

## 6. 插件安装、激活与回滚

```text
验签清单 → 下载完整包 → 校验并准备不可变目录
→ 再确认无运行/等待任务 → 官方 profile 写锁内切换 manifest
→ 提示重启 → 加载新版本 → 验证实际解析与客户端
```

- 包含生产依赖与构建客户端；校验 Ed25519、SHA256、尺寸、引擎范围、平台和架构。
- 解包拒绝路径穿越、链接、重复路径及超额内容，不执行未知生命周期脚本。
- 版本在 profile 的 `.benchgo/releases/`；准备完成后原子切换激活指针，保留上一版回退。
- 正式更新不覆盖运行中代码；升级与回退都在重启主机后生效。
- 有运行或等待交互的任务时禁止安装/回退，下载后再次检查；检查、下载、配置和激活互斥。
- 失败保留可运行版本；下载结束、目录存在或 manifest 版本不等于激活成功。
- 回滚也检查任务状态、完整包和引擎兼容，保留用户配置、会话与禁用选择。

官方 runtime 不内置锁死的 BenchGo 插件；离线种子在 `resources/benchgo/seed`。安装器使用随应用提供的 Node 登记 profile，无需用户另装 Node/包管理器；profile 通过 `link:` 依赖组合包装器，避免重复安装私有依赖。

## 7. 安装迁移与解析一致性

旧内置插件或 profile 顶层同名实体可能遮蔽新版。迁移须同时核验 manifest、物理包和官方解析器得到的元数据/入口/client 路径，不能只查版本目录。

- 旧内置插件需一次新版应用安装，不能用 profile 同名包覆盖安装目录优先解析。
- 应用关闭后，在官方写锁内仅移除已验证归属 BenchGo 的遮蔽物；配置写入失败恢复原包。
- 运行中独立更新遇遮蔽，提示关闭应用重新安装，不搬动已加载代码。
- 新 EXE 可离线升级到内附插件，但保留用户更高独立版本、主动禁用和会话配置。
- 覆盖同版本重装、原位升级、重复安装、回退、写入失败、短/长路径和真实官方解析。
- 内部 `commander` 协议、数据目录和兼容标识保留，界面统一 BenchGo。

共享服务双实例/作用域问题尚未完成指定真实双会话验收。安装文件一致不能证明该问题已消除，正式发布需补运行态兼容证据。

## 8. 签名与分发渠道

| 渠道 | 用途 |
| --- | --- |
| `plugin-v<version>` | 不可变完整插件包 |
| `plugin-updates` | 独立插件签名元数据，避免应用 GitHub latest 干扰 |
| 应用版本 Release | Windows 安装包与正式 Android APK |
| `app-updates` | 应用自动更新包、SHA512 `latest.yml` 和 blockmap |

渠道指向 `zhuogo/BenchGo`，不使用官方 DeepSeek 应用更新源。仓库/资产须允许匿名下载，客户端不携带 GitHub 凭据；镜像不能绕过私有发行权限。

插件公钥为 `plugins/benchgo/shared/update-public-key.pem`，私钥只在受保护的本地忽略目录和 CI Secrets，另行安全备份，不提交仓库；密钥生成拒绝覆盖。原生应用复用官方 electron-updater，插件采用独立签名信任链。

Android 持续使用同一发行密钥，正式包不可调试，debug 不进入发行。Windows 未配 Authenticode 时不得宣称发行者认证；插件 Ed25519 不等于 EXE 发行者签名。

## 9. 发布操作与门槛

1. 确认交付单元，递增相应 manifest/锁定文件版本；不覆盖公开不可变版本。
2. 插件运行 `BenchGo plugin update`：初始化官方子模块、锁定依赖、构建、package-layout 闭包检查，再生成完整包与签名清单；默认 artifact，显式 publish 才分发。
3. Windows 运行 `BenchGo Windows installer`，通过打包运行和静默安装后，由 `Publish verified Windows installer` 发布。
4. Android 运行 `BenchGo Android package`，核对版本、发行证书、不可调试、原生及内嵌资源后发布。
5. 插件清单锁定已验证引擎范围；升级引擎重验兼容，不据旧测试扩大范围。
6. 发布后从匿名 GitHub 与默认镜像取回清单、签名和完整包，核对尺寸、SHA256/SHA512、blockmap、构建提交和版本关联。

完整包与签名元数据都成功分发，才算客户端可下载；CI 成功、面板已接入或 artifact 存在不等于正式发布。

## 10. 实现边界与验收条件

已有五入口装配、构建闭包检查、签名更新、独立版本比较、不可变激活/回退、安装迁移和平台工作流。历史发行及测试只证明当时产物；本次文档整理未重跑构建、签名、安装或发布。

每次发行至少确认：

1. 源码、产物、安装和实际加载版本一致，五入口及客户端可用；官方子模块未被品牌注入修改。
2. 签名、摘要、尺寸、平台、架构和引擎错误均拒绝；失败和回退不损坏用户数据。
3. Windows 原生验证 packaged smoke、新装、修复重装、原位升级、强杀后同档案重启、旧锁恢复和实际模块解析。
4. Android 核验连续发行签名、版本和资源，实测主机更新后重连；APK 更新与主机更新分开验证。
5. 模型、配置、会话、工作区、禁用状态和原生句柄保留。
6. 真实档案与用户场景单独验收；源码/隔离测试不代替正式安装、自动更新或公网部署。
7. 全量测试注明串行或分文件/并发、总数及失败，不删改或放宽断言凑绿；按改动选择检查，不默认跑整个上游套件。
8. 发行证据放在构建/发布记录和产物中，设计只维护机制、边界与验收条件，不积累逐次日志。
