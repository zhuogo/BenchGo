# 更新与发布设计

本板块负责应用、插件与移动端的打包、签名、分发、安装迁移和更新。总体关系见[总架构](../总架构.html)，源码装配见[源码架构](../02-工作台与Agent/源码架构.md)。不在本文维护逐版本流水账，当前版本以 manifest、引擎 pin 和实际发行产物为准。

## 1. 交付单元与版本来源

| 单元 | 版本与内容 | 更新边界 |
| --- | --- | --- |
| 桌面应用 | 根 `package.json`；Electron、官方 Harness、启动/托盘/安装器和离线插件种子 | 壳层、引擎、原生能力、安装器变更需要应用安装包 |
| `benchgo-plugin` | `plugins/benchgo/package.json`；五源码包业务与统一客户端 | 主机页面、工具集成、SuperAgent、Voice、Link 主机端随插件更新 |
| Android | `plugins/link/mobile/android/app/build.gradle`；独立 `versionName`，`versionCode` 递增 | 原生能力、壳层和 APK 内置连接页面需更新 APK |
| macOS 桌面 | 根 `package.json`；原生 arm64 / x64 runner 分别构建 DMG、ZIP | 复用官方打包工厂与 BenchGo 离线种子；当前 ad-hoc 签名，未 Apple 公证，通过官网手动下载更新 |
| Linux 服务端归档 | 根 `package.json`；离线插件种子、bootstrap、安装入口、校验和许可 | Ubuntu / Debian x64、systemd 用户服务，首次联网获取官方运行时；不是 Linux Desktop，当前不支持 ARM64 |
| 服务器工作台/中继 | 各自 CLI 和服务生命周期 | 两者不互相隐式安装，见[设备连接](../01-设备与远程连接/设计.md) |

采用「统一入口、按需更新」：对外发行使用一个 BenchGo 版本，应用、功能包、Android 保留独立组件版本和兼容条件；普通用户无需选择组件。只改插件无需重编安装包；手机访问主机提供的页面时，升级的是当前连接主机，重启后重连/刷新即可，不能把主机插件提示当成 APK 更新。

统一发行版记录在签名清单的 `releaseVersion`，功能包内以 `package.json` 的 `benchgo.releaseVersion` 记录随包安装的发行版基线。EXE/APK 没有变化时沿用对应旧组件，不为对齐展示版本重新封装；功能包也可复用。主机成功验签并确认本机相关组件均已满足、引擎兼容且没有待重启版本后，可在本次运行中确认新的统一发行版。未知应用版本不确认，失败检查保留此前已确认版本并提示重试，较旧清单不能降低展示版本。尚无基线或已验签确认时不猜测，内部版本仅在详情中显示。

官方引擎以 `upstream.json` 和 `deepseek-harness/` 子模块 pin 为真源。升级从官方 `origin/master` 获取提交，同步两处并重验兼容；不改官方源码，不恢复社区 Stable/Beta/Next 或 runtime patches。

## 2. 插件发布闭包

源码包、五个 Cordis 入口、统一客户端与生成目录以[源码架构](../02-工作台与Agent/源码架构.md)为准，最终只安装和更新一个 `benchgo-plugin`。发布时检查：

- 完整包脱离源码同级目录仍可运行，不携带旧业务副本、`.bak*` 或补丁临时文件。
- 检查五入口、runtime、资源导入和客户端发现；后端入口可解析不能替代客户端加载验证。
- 官方共享服务须保持宿主模块/作用域身份；版本相同或链接目标看似相同，不足以证明运行时单实例。

## 3. 构建与开发加载

本地构建命令、Windows 预览与网页热加载流程见[源码架构](../02-工作台与Agent/源码架构.md)。开发加载与正式发行分别验证；网页重载不构建服务器种子，也不等于完整发布。

正式打包须从当前源码重建，记录构建提交并核对安装后的实际源码、客户端、插件与引擎。`npm run check` 只查版本、工作区和入口一致性，不代替构建或运行验证。

## 4. 品牌与平台身份

应用、插件和移动端均名 BenchGo，Windows 主程序为 `BenchGo.exe`。保留既有 applicationId、appId、协议、用户数据目录，确保原位升级与数据连续。

图标唯一来源为 `assets/brand/benchgo-app.svg`（带背景）和 `assets/brand/benchgo-mark.svg`（透明），是同一形象。窗口、托盘、安装/卸载、启动初始化、Android、网页 favicon、五入口统一复用；供应商品牌与第三方版权保留原归属。

Windows “应用”菜单顺序：关于 BenchGo、管理 dsh 命令、重启、退出。关于窗口使用 BenchGo 品牌和 `https://benchgo.cn`，引擎归属为补充。更新在 BenchGo 面板，不恢复原生“检查更新”菜单；重启走安全流程，失败明确返回，不静默退出。

## 5. 更新入口与状态

侧栏只有「更新」入口，弹窗保留品牌、简短状态与一个主操作，读取当前连接主机的统一决策。检查失败仅在弹窗内显示原因与重试，不在侧栏另加失败状态条。有可用更新时，鼠标、触屏或 Space / Enter 按住 2 秒才执行，期间匀速填充，提前松开、移出、取消、失焦、隐藏或关闭均取消；减少动效不缩短确认时间。组件版本、主机标识及更新内容收进信息图标，点击后以轻量气泡展开；来源在底部一行切换，默认国内加速，不展示说明段落。不提供两条平级更新路线。

- 当前版本已知且验签清单版本严格更高，才提示对应组件有更新。
- 主机返回 `decision` 决定功能包、应用、待重启、维护者部署或兼容阻碍；前端按决定执行，不让用户挑选 EXE 或插件。兼容的新功能包优先，生效后仍有应用更新时继续提示。
- 签名清单可声明 `minAppVersion`；同引擎但需要新桌面能力时也先走应用更新。未知版本拒绝猜测，当前引擎高于兼容上限时提示等待兼容版，不诱导降级。
- 未检查、检查失败、版本未知、已最新、已准备待重启分别显示；未知不能显示已最新。
- 红点只代表确认的新版本或待重启插件；加载新版本后清除，不重复安装待生效版本。
- 服务器显示由服务器部署管理，不要求安装 Windows EXE；清单 404 是通道未就绪，签名/权限/包下载失败仍按错误处理。
- 签名清单、签名文件与功能包均使用所选来源；默认源为 `https://ghfast.top/`，可选 GitHub 直连或自定义 HTTPS 镜像；失败保留选择，不静默换源。
- 桌面检查通过官方 Desktop bridge；原生自动更新使用 BenchGo 配置的内置源，面板签名安装包链接遵循所选来源。
- 本机桌面复用官方更新器的状态、订阅和确认流程，产品页面不向原生安装器传入任意下载地址。远程页面只能更新连接主机的功能包；需要应用更新时提示到主机完成，不操作访问者电脑。
- Android 设备页检查「本机应用」，只比较已验签的 `android.versionCode`；签名清单包含 APK 版本、不可变地址、大小与 SHA256。需要安装时交给系统浏览器与 Android 安装确认，页面不宣称已对下载后的 APK 做哈希验证。远程工作台不暴露原生桥，不能借主机更新安装手机应用。
- 有任务时不强制安装或重启；功能包准备后明确提示重启主机，Android 安装保留系统确认。无通道、缺手机元数据、网络和签名失败均不能冒称已最新。

## 6. 插件安装与激活

```text
验签清单 → 下载完整包 → 校验并准备不可变目录
→ 再确认无运行/等待任务 → 官方 profile 写锁内切换 manifest
→ 提示重启 → 加载新版本 → 验证实际解析与客户端
```

- 包含生产依赖与构建客户端；校验 Ed25519、SHA256、尺寸、引擎范围、平台和架构。
- 功能包压缩体积上限为 512 MiB；下载边落盘边计算 SHA256，验证签名清单声明的大小与摘要后才解包，不将完整包积存在内存。失败清理部分下载，不覆盖既有文件。解压上限为 1 GiB、60,000 条目；打包前按真实依赖解析去重，保留许可证及 Windows 使用 WSL 所需的 Linux worker。
- 解包拒绝路径穿越、链接、重复路径及超额内容，不执行未知生命周期脚本。
- 版本在 profile 的 `.benchgo/releases/`；准备完成后原子切换激活指针。
- 正式更新不覆盖运行中代码，重启主机后生效。
- 有运行或等待交互的任务时禁止安装，下载后再次检查；检查、下载、配置和激活互斥。
- 失败保留可运行版本；下载结束、目录存在或 manifest 版本不等于激活成功。

官方 runtime 不内置锁死的 BenchGo 插件；离线种子在 `resources/benchgo/seed`。安装器使用随应用提供的 Node 登记 profile，无需用户另装 Node/包管理器；profile 通过 `link:` 依赖组合包装器，避免重复安装私有依赖。

## 7. 安装迁移与解析一致性

旧内置插件或 profile 顶层同名实体可能遮蔽新版。迁移须同时核验 manifest、物理包和官方解析器得到的元数据/入口/client 路径，不能只查版本目录。

- 旧内置插件需一次新版应用安装，不能用 profile 同名包覆盖安装目录优先解析。
- 应用关闭后，在官方写锁内仅移除已验证归属 BenchGo 的遮蔽物；配置写入失败恢复原包。
- 运行中独立更新遇遮蔽，提示关闭应用重新安装，不搬动已加载代码。
- 新 EXE 可离线升级到内附插件，但保留用户更高独立版本、主动禁用和会话配置。
- 覆盖同版本重装、原位升级、重复安装、写入失败、短/长路径和真实官方解析。
- 内部 `commander` 协议、数据目录和兼容标识保留，界面统一 BenchGo。

共享服务的模块与作用域身份须在安装版真实档案中验收：主聊天与未归档旁聊同时在线时，能够创建执行会话、写入记录并完成任务。安装文件一致不能替代运行态兼容证据。

## 8. 签名与分发渠道

| 渠道 | 用途 |
| --- | --- |
| 统一 `v<releaseVersion>` | 不可变功能包、当次变化的 EXE/APK、签名清单与来源记录；历史 `plugin-v<version>` 只保留旧兼容下载 |
| `plugin-updates` | 独立插件签名元数据，避免应用 GitHub latest 干扰 |
| 应用版本 Release | Windows 安装包与正式 Android APK |
| `app-updates` | 应用自动更新包、SHA512 `latest.yml` 和 blockmap |

统一发版继续复用上述下载通道；正式 `v<releaseVersion>` 同时保存发行来源与签名清单，未变化组件保留原不可变下载地址。macOS 双架构和 Linux 服务端随显式发行重新构建，独立记录平台、架构、源码和校验结果，不冒充 Windows 自动更新组件。`downloads.json` 与 Ed25519 签名列出全平台实际资产、SHA256、大小和 macOS 公证状态；`SHA256SUMS.txt` 覆盖发行文件。官网从 GitHub 实际资产决定可下载状态，失败和缺失不得显示成功。日常 Git push 只保存源码，不更新任何正式通道。

渠道指向 `zhuogo/BenchGo`，不使用官方 DeepSeek 应用更新源。仓库/资产须允许匿名下载，客户端不携带 GitHub 凭据；镜像不能绕过私有发行权限。

官网通过同仓 `release-metadata` 分支的 `releases/v<releaseVersion>/downloads.json` 与 `.sig` 读取支持浏览器跨域的原始签名字节。发行流程在不可变资产公开并核验后、正式更新通道推进前自动同步；核对公开 Release、标签提交、资产原字节与 Ed25519 签名，保留历史目录及其他分支文件，拒绝覆盖不同内容且不强推。官网仍以固定公钥验签并核对发行版本、源码提交及实际资产，目录不可用时只回退到真实 Release 资产，不宣称验签成功。已有发行可用 `node scripts/release/publish-web-catalog.mjs --directory <发行元数据目录> --version X.Y.Z --source-sha <40位提交>` 幂等补同步，不重建或改写已发安装包。

插件公钥为 `plugins/benchgo/shared/update-public-key.pem`，私钥只在受保护的本地忽略目录和 CI Secrets，另行安全备份，不提交仓库；密钥生成拒绝覆盖。原生应用复用官方 electron-updater，插件采用独立签名信任链。

Android 持续使用同一发行密钥，正式包不可调试，debug 不进入发行。Windows 未配 Authenticode 时不得宣称发行者认证；插件 Ed25519 不等于 EXE 发行者签名。

## 9. 发布操作与门槛

1. 维护者只使用统一发版入口；普通 push 不发布。源码提交后用 `npm run release:plan -- --version X.Y.Z` 生成按需构建计划，比较上一个正式统一发行的源提交；首发无可信基线时完整构建。GitHub Actions 入口为 `BenchGo unified release`，填写统一版本与发布说明；默认 `publish=false` 仅生成计划，显式 `publish=true` 才构建、验证、签名并发布。
2. 只递增变化组件对应 manifest/锁定文件版本，并选择统一发行版本；不覆盖公开不可变版本。功能包变化不要求根应用版本跟着增加；Windows 与 Android 组件版本也独立，只改桌面原生能力无需递增 Android 版本或重打 APK，只改手机原生能力亦不重打 EXE。
3. 统一流程调用插件、Windows、Android、macOS 双架构和 Linux 服务端构建验证：插件构建完整依赖闭包并验签，Windows 保留打包运行、新装与迁移验证，Android 保留发行证书、不可调试和资源检查；macOS 使用原生对应架构 runner 验证运行时、离线种子、登记代码和启动品牌，Linux 校验种子摘要、安全归档、x64 worker 和当前 bootstrap，并在干净用户与真实 systemd 下完成安装、认证连接及重启验证。不能以计划检查代替构建验收。
4. 所需构建全部通过后再组装同一发行：复用未变组件、生成签名清单与来源记录，发布不可变版本资产，最后更新正式通道。预演只产出计划或构建 artifact；不得推送标签或改变用户可见更新。
5. 插件清单锁定已验证引擎范围；升级引擎重验兼容，不据旧测试扩大范围。
6. 发布后从匿名 GitHub 与默认镜像取回清单、签名和完整包，核对尺寸、SHA256/SHA512、blockmap、构建提交和版本关联。

完整包与签名元数据都成功分发，才算客户端可下载；CI 成功、面板已接入或 artifact 存在不等于正式发布。

## 10. 实现边界与验收条件

已有五入口装配、构建闭包检查、签名更新、独立版本比较、不可变激活、安装迁移和平台工作流。统一入口、主机决策、Android 本机更新与按需发布属于同一机制；源代码验证不代表正式通道已发布。旧 EXE/APK 要先获得带统一入口的版本，不能追溯改变已安装原生代码。构建、签名、安装与发布须针对对应发行产物分别验收，历史发行及测试不替代当前产物验证。

每次发行至少确认：

1. 源码、产物、安装和实际加载版本一致，五入口及客户端可用；官方子模块未被品牌注入修改。
2. 签名、摘要、尺寸、平台、架构和引擎错误均拒绝；失败不损坏用户数据。
3. Windows 原生验证 packaged smoke、新装、修复重装、原位升级、强杀后同档案重启、旧锁恢复和实际模块解析。
4. Android 核验连续发行签名、版本和资源，实测主机更新后重连；APK 更新与主机更新分开验证。
5. 模型、配置、会话、工作区、禁用状态和原生句柄保留。
6. 真实档案与用户场景单独验收；源码/隔离测试不代替正式安装、自动更新或公网部署。
7. 全量测试注明串行或分文件/并发、总数及失败，不删改或放宽断言凑绿；按改动选择检查，不默认跑整个上游套件。
8. 发行证据放在构建/发布记录和产物中，设计只维护机制、边界与验收条件，不积累逐次日志。
