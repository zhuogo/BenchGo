# 持续主会话后端：持久输入与安全恢复

2026-11-05 源码核对。持久消息 inbox、工单/验收恢复、官方 composer 文本/引用接入已落代码并有定向记录；真实桌面输入及重启未验收。派工后的聊天回应由 Router 自然生成，替代固定接单文案；普通 Router 正式流式已有真实供应商通过记录。沿用已有持久账本、工单、订阅、outbox 和 Harness，不修改官方或参考源码。

## 约束

Router 兼任面向用户的聊天助手与总调度，负责理解需求、回答和协调；网页、文件与 shell 调查交给 Worker，所有调查执行自动委派，不把创建工单作为额外审批。明确原始用户消息是派工依据，后续真实副作用继续执行现有授权检查。主聊天、旁聊统一模型设置，来源隔离。

消息先持久入队并返回接收回执，再由每会话串行短 Router 回合分诊；Router 运行时仍可接受新消息。重启通过原消息 ID 与官方 transcript 对账，不盲目重放。处理中不覆盖其他请求，队列保留故障/阻塞状态。取消与清空必须有明确队列语义。

桌面工单与 Assignment 可靠落库后，派工工具返回当前 Router；Router 按对话自然回复，通过正常文本终答或 `assistant_reply` 发布，不插入系统固定接单句，也不等待 Worker。显式人类渠道请求复用同次 Router 研判的 `replyText`，开单成功时将该正文与工单、原来源一起写入 outbox 并去重；没有正文时不补模板。待发回复若已被结果或停止状态取代则抑制，旧固定待发回执不再投递。渠道仍是至少一次投递，不承诺外部绝对只收一次。Worker 完成后由 Router 的证据验收调用同时生成交付正文，不另唤醒主聊天生成第二份摘要。验收异常保存可诊断状态与恢复路径，授权变化、停止、版本变化均在代码复核。

补充、查询、停止复用工单管理与订阅，避免重复建单。目标与自动化复用现有调度；主动消息仍需检查事实有效性、偏好和去重。

## 接口与验收

公开消息回执区分 `queued`、`processing`、`processed`、`failed`、`uncertain`、`cancelled`，不将接收成功称为执行完成。`history.requests` 与持久 `state.requests` 保留原请求 ID；重试使用相同 `requestId`，同 ID 不同消息拒绝，取消后仍保留去重回执。`cancel` 取消当前会话排队请求并取消 Router 回合；`resetMain` / 主聊 `/clear` 取消旧队列、清理主会话绑定并保留请求去重记录，不撤销独立后台工单。

`send({threadId,text,requestId,replyContext?})` 返回 `threadId/sessionId/requestId/messageId/status`；同 ID 的指纹包含正文与可信回复关联，关联变化也不能覆盖旧请求。`requestState({threadId})` 返回该逻辑 thread 的持久收件数组；`history.requests` 仅投影当前模型 session 以及尚未绑定 session 的有效请求，清空后不把旧会话回执重新塞进新聊天。内部 `prepared` 表示提交准备状态，不是完成。断线/重启先按同 ID 与官方日志对账，不因未知回执自动再发。

渠道内部 outbox 的 `ticket.accepted` 携带 AI 生成正文及其来源标记、`ticketId`、`source`、`requestId` 与可选 `sourceEventId`；其中 `requestId` 是来源 Trigger ID，不是 `send` 的请求 ID。桌面派工回应属于普通 Router 聊天回复，不生成此事件。`ticket.result` 携带 `ticketId`、`source`、`instructionRevision`、`resultVersion`、`publication`；不要假定所有通知都有 `requestId`。公开通知投影保留工单、线程和版本等白名单字段，不返回完整 `source`；前端目前按 `ticketId` / `threadId` 关联，若要精确定位到 inbox 请求，还需核对工单来源消息与请求 `messageId`，不能直接把两种 `requestId` 等同。

验收覆盖连续三请求、重启、去重、权限收窄、后台任务不阻塞聊天、派工成功后的自然回复、渠道接单回复与工单一致、验收异常可恢复、来源隔离。eval 保留结果与 HTML 报告，真实模型/实际渠道/模拟验证分别说明；既有验收记录不代表本次自然回复调整已完成真实模型或渠道验收。

## 前端接入约定（代码已接入，真实桌面待验收）

主聊天发送应调用 SuperAgent `send`，保存并展示返回的 `requestId`、`messageId` 与 `status`；轮询或刷新 `history` 时读取 `requests`，其中 `processed` 只代表 Router 回合结束。取消调用 `cancel`，不得把取消解释为已撤销后台工单。桌面派工后的自然回复沿用正式聊天投影；后台结果通过通知事件按 `ticketId` 和原来源回填当前会话，并遵守上述请求 ID 区别。

官方 composer 通过公开 Slots 适配提交与停止，SuperAgent 文本与可解析引用进入 `engine.send`；其他命令仍用原命令面，主聊 `/clear` 进入持久取消/清空流程。附件当前不支持持久收件，显示系统状态并保留文字/附件草稿，不静默退回直接 followup。适配层保留原 requestId、串行去重、断线核对，页面重开只对账，不盲目重发。逻辑 thread 的 sessionLineage 保留旧/新模型 session 归属，清空后仍可查询、补充、取消原单或回答 Attention，不能跨旁聊管理。

消息展示已使用 `client/quiet-chat.jsx` 消费发布投影、正式回复流和持久通知，过程工具日志不进入聊天正文；这与发送端是否接入 inbox 是两件独立事项。桌面源码入口为 `src/message-inbox.mjs`、`src/engine.mjs`、`src/chat-publication.mjs`、`client/conversation.jsx`；`src/ticket-ack.mjs` 仅承载渠道 AI 接单回复入队。

正式流式使用官方顶层 assistant_reply 参数或 partial.blocks 的 text 增量，session/turn/request 三者一致才显示；正式发布优先替换同一 reply 身份，completed 后由持久投影取代暂存，取消/失败清除未提交正文。工具参数、推理块和 Worker 原文不混入聊天，不新增渠道流式协议。详见[正式回复流式](正式回复流式.md)。

2026-11-04 显示约定：持久通知中的交付正文以普通助手消息呈现，不显示独立通知卡或「标记已读」入口；必要选项继续使用原事件回复协议。此显示调整保留通知账本、来源与版本校验，不改变后端投递回执。

## 已实现：验收异常与恢复

原证据重审、Worker 补查/纠错与 Attention 答后续行是三条不同入口。按[任务结果验收矩阵](任务结果验收矩阵.md)，`ticketRetryReview` 只重审原证据；`unchanged` 是输入去重结果，不是唯一后续操作。P0 已接原 Ticket/Assignment/Run/session/工作区续做，失败附 AI 自然说明和修正指令；桌面/飞书 Review Attention 保存原问题和真实答案，回答后走原分派，不冒充 Worker 原生 question call。真实返工/阻塞验收仍未完成。

执行完成后的模型/证据复核故障保存为 `waiting`，`review.waitKind=review_wait`、`review.retryable`、`review.diagnostic` 记录分类与脱敏阶段、错误码和时间，不保存供应商响应原文。执行已完成不因验收故障改成是否执行未知。可重试核验按持久退避进行：起始 30 秒，指数增长且封顶 15 分钟；无“两轮后终单”门禁，并发同单核验合并。停止、版本、权限和预算优先；不重复投递同类系统状态，不能承诺基础设施必然自动恢复。需要用户信息/权限/范围决定才建立 blocked Attention，内部故障不让用户替系统核实事实。

无进展或资源不足保留 `continuation_wait`。`ticketResume` 续做等待必须提供当前 `expectedResultVersion`，`additionalExecutionMs` 为安全整数 0..600000、缺省 0；执行额度等待必须显式给正数，0 不加额度或排队。Goal 限额须经原预算接口调整，不因追加执行时长而绕过。恢复前核实原执行已停、官方 writer、run/session/fence、checkpoint/transcript、当前版本及授权；回 `queued:false/code` 时仍是等待，效果未知不重放。原 Assignment/Run/session/目录继续，不重建空白成果。

旧 `open/uncertain` 且 `resultVersion=0` 的记录允许 owner 使用 `expectedResultVersion=0` 恢复核验：必须独占原官方 session、校验 transcript hash、run/fence、当前授权、工单修订，且不能有待执行的新上下文；只排入 verificationOnly，不重跑 Worker。已发布 waiting 的恢复继续使用版本 CAS。停止或授权变化不能被迟到核验覆盖。

历史生产异常没有保存具体错误，因此不能从离线 HTTP 非流式复核成功推断其官方流式失败根因。新增诊断用于后续实际运行定位，历史工单保持只读、未自动重发。
