# SuperAgent 设计

本文件是 SuperAgent 板块的总览：定位、原则、模块导航和共同验收边界。具体机制在下表对应的模块文档各维护一份，这里不重复。板块间关系见[总架构](../总架构.html)，本板块图解见[架构图](架构.html)。

## 定位与范围

SuperAgent 是 BenchGo 面向个人的总助手，承担持续对话、事件研判、任务编排和结果交付。用户始终和同一个助手（Router）对话；需要动手的事开成工单，由 Worker 在后台执行，做完后 Router 把结果告诉用户。

一条请求的路径：

1. 消息进入。桌面主聊和旁聊直通 Router；渠道消息先过准入，高噪音来源再经研判。
2. Router 能答的当场答；要动手的开工单，然后继续和用户对话。
3. 一张工单对应一个官方 Worker 会话；会话内的拆分使用官方 subagents。
4. Worker 正常结束，系统保存它的最后一段话作为结果，工单记为完成并通知 Router。
5. Router 读结果，用自己的话告诉用户，没做成就直说；outbox 把这段回复送回原来源。
6. 用户不满意时让 Router 开关联调整单。

工单只有“进行中、等待、完成”三态，执行完成与送达分开记；规则见[结果与交付](结果与交付.md)。目标是用户的关注清单和主动性的源点，见[目标清单](任务与执行.md#目标清单)。首轮以单机桌面加飞书闭环为基线，渠道扩展和多端不是本地任务执行的前置条件。

## 原则

- **确定性的事交给代码**：身份、准入、去重、状态、权限、索引、计数和投递。模型负责理解、入口研判、执行和 Router 的自然表达。
- **原始要求与真实执行记录是权威**：模型生成的摘要和权限描述不能授予权限；工单的状态变化由宿主根据官方执行的结束事实决定。
- **复用优先**：Router 和 Worker 都是官方 Agent 会话；不新建平行的会话系统、推理循环、定时器或任务数据库。
- **做减法**：一张工单一个 Worker，委派用官方 subagents，审批只用任务内审核，结果直接保存；不设内容验收、自动返工和执行预算闸门。
- **少占注意力**：后台通知只在结果可用、明确失败或确需用户决定时出现，不限制用户正在聊天时的正常回答。
- **渠道只是适配器**：协议、来源核对和本渠道的使用者权限归适配器；核心不区分主人与其他人的权限档位，渠道不保存独立的对话状态或第二份工单账。

## 模块与服务边界

五个源码包交付一个 `benchgo-plugin`。SuperAgent 的 Cordis 入口是 `benchgo-plugin/superagent-plugin`，提供 `assistant` 服务，依赖 Harness 聚合的 `commander`；`assistant` 的工具名、HTTP 路径和数据目录不随源码包改名。

| 组件 | 职责与边界 |
| --- | --- |
| BenchGo 基础层 | 公共配置、模型目录与凭据、数据根、客户端装配和共享资源 |
| 官方 Harness | Agent、会话、模型调用、工具、审批、Schedule、skills、原始日志和运行环境 |
| Harness 聚合 / commander | 原生 Agent 接入、会话聚合和适配。工单 Worker 直接使用官方 `ctx.agents`，不启动原生 CLI |
| SuperAgent / assistant | 入口研判、工单、授权快照、分派、订阅、结果保存、Router 表达与投递、学习和恢复协调 |
| Voice | ASR、TTS、通话和语音配置。主聊与旁聊的通话复用原 Router，见[实时通话](../03-实时语音/实时通话.md) |
| Link | 多端认证和既有服务转发，不直接读 SuperAgent 的私有数据库 |
| 渠道适配器 | 协议收发转换、账号与来源映射、消息归一和能力声明。准入与研判的现状见[入口与研判](入口与研判.md#已敲定的身份边界与当前差距) |

Router 与 Worker 之外，入口研判、分派领取、投递、执行摘要、自我迭代和监督都是后台服务，其中部分会调用模型，但不是常驻的 Agent。自我迭代是一大组四小组、11 项职责，Router 同步记忆加一个专用后台执行器；Watchdog 只监督。后台迭代不建工作台聊天、工单或过程 UI，机制仅在[记忆与技能](记忆与技能.md#自我迭代一大组四小组11-项职责)维护。主要源码文件的分工见[服务契约](服务契约.md#公共接口与数据契约)。

## 共同验收边界

各模块的已实现、待实施和待验证项在所属文档的文末维护，不另立现状或验收流水。

- 源码、生成产物、安装目录和运行实例分别核实。`npm run check` 只检查版本、工作区和入口的一致性。
- 源码接线和定向测试不等于安装版已验收；隔离 profile 下的真实模型请求也不能替代正式档案的验证。
- 安装版的主路径验收：普通问答不开单；执行请求派工后，Worker 正常结束即完成并通知 Router，Router 自然表达并送回原来源；异常结束、待审批、待输入、暂停和停止显示为等待并写明原因；表达或投递失败只重试对应阶段；运行中重启后能恢复。
- 前端检查空、加载、错误、有数据四态，视觉由用户最终验收。
- 测试报告注明提交、运行环境、整跑或分文件、总数与失败数，不删除或弱化安全断言。真实验证保留 Trigger、Ticket、Run、Result、Delivery 的关联和实际工具调用；工具目录存在不证明能力可用。
