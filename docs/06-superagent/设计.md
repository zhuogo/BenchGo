## 基础特征

SuperAgent 区别于普通聊天式 AI 的四个基础特征，本设计的全部机制都是为这四点服务的：

- **连续**：对话与任务不因会话结束、进程重启而断线。靠文档链路开局注入（醒来就接上）、工单状态机与订阅（活干到哪算哪）、账本原文可查（原话永远在）、存算分离（主会话可换、状态不断）。
- **高效**：人的注意力、模型的 token、系统的调度都不浪费。靠占最少注意力（不该开口不开口）、Gate 代码过滤（不该研判的不研判）、Inline & Spill（不该进上下文的不进）、计数器触发沉淀（不逐回合纠结）、辅助模型分工（杂活不占主模型）、Worker 并行（活不排队）。
- **主动**：不等吩咐也能动——事件来了自己分类研判、定时任务自己触发、异常自己处置、经验自己沉淀。但主动有界：以书面规则为界，无规则先只记录；主动是「占最少注意力」的另一面，动得越多、越要安静。
- **持久**：身份、记忆与能力随时间累积而不蒸发。靠双记忆（提炼层越老越值钱、账本层全量留痕）、技能沉淀与策展（能力只增不丢）、工单档案可审计、检查点可回滚。系统越用越懂主人，这是「持久」与「连续」的区别：连续是不断线，持久是能积累。

## 1. 总原则

1. **占最少注意力（总原则）**：后台主动通知只在人必须行动、或结果可用时发出；其余时间安静干活。用户正在聊天时，Router 正常交流、回答与回应派工，不受这条通知规则限制。主动工作无书面规则先只记录、不动手；用户明确请求按原授权推进。
2. **确定性问题交给确定性机制**：准入用代码、回忆用 ID 绑定、搜索用索引、触发用计数器、关键动作留指令入口。模型只在真正需要判断的地方出现（研判、沉淀什么、干活本身）。
3. **效果优先，消耗其次**：设计与运行以效果为约束；在保证效果的基础上，再把消耗降到最低。便宜档只在「效果相当」时成立，效果有差立刻用强模型。
4. **分级交付**：没事不报；要报给结论 + 证据；需要拍板才摆问题。与原则 1 是一对：一个管开口频率，一个管开口规格。
5. **进化不看忙闲**：记忆整合、技能沉淀是定额工作，按计数器触发、后台并行，不等系统空闲。
6. **规矩归文档，机制归系统**：能用 prompt 写成文档约束的（审批红线、渠道规矩、保险库使用规矩）归文档链路；必须有活物执行的（Watchdog、保险库的录入代填机制）归系统实现。

## 2. 总体架构

三组结构，组间各只有一条总线：

```
┌─ 用户端组 ──────┐   消息进来   ┌─ SuperAgent 组 ──────────────────────────────┐   结果输出   ┌─ 输出组 ─┐
│ 桌面工作台（本体）│ ─────────→  │  判断器 →（组管道 / 个体直达）→ 评估与工单     │ ─────────→  │ 结果交付  │
│ 微信 / 飞书 / …   │             │        ┌─ 内置组 ──────────────────┐        │             │（即给用户）│
└──────────────────┘             │        │ Router 主会话 ⇄ Worker 池  │        │             └──────────┘
                                 │        │ Watchdog（组内监督）       │        │
                                 │        └────────────────────────────┘        │
                                 │  积累与进化（虚线挂内置组，后台机制）          │
                                 └───────────────────────────────────────────────┘
```

- **用户端组**：人进来的地方。桌面工作台是本体入口；微信、飞书、邮箱、日程等为外延渠道，可继续增减。
- **SuperAgent 组**：引擎本体。含入口判断器、组通道管道、评估与工单层、内置组；积累与进化以虚线（后台机制）挂在内置组上。
- **内置组**：执行核心 = Router 主会话 + Worker 池 + Watchdog（组内监督员）。
- **输出组**：默认即给用户输出。结果交付在此完成分级交付，回到来源渠道找用户。不再向外延伸连线。

## 3. 入口与判断器

### 3.1 判断器（入口第一站）

任何渠道的消息进来，**不先读文档、不先连主会话**——因为此时无法判定它是否归主会话管。先过判断器：

- 职责：判明来源渠道与会话结构，给消息定性，再分路。判完才路由。
- 判断是代码与规则完成的确定性动作，不消耗模型研判。

### 3.2 两层分流

**筛选档：高噪声输入（群聊 / 多方会话 / 自动采集事件等）**
按噪声与来源性质分流，不按渠道名一刀切。多人讨论或自动采集不等于主人授权，先归一为 Trigger、过 Gate，按量窗口化后形成候选卡（见 §4）；不能把未经筛选的原始消息流交给 Router。

**直通档：用户主动输入（包括已验证的一对一消息）**
说话者即对话方，无旁观者、无噪声、上下文连续：

- **不启用压缩与窗口化**（Inline & Spill 不上场），消息直达主会话；
- 默认场景是主人一对一（工作台直发即属此类），属 explicit 直通，跳过 Eval 的“接不接单”裁决；仍登记 Trigger、去重留痕，由 Router 理解需求，必要时开工单与分派；
- 预留：非主人的一对一（如客户私聊）不压缩、但需身份与信任判断，此项为预留设计，尚未定版。

### 3.3 定时与系统事件

定时任务、系统通知等非人来源，以合成 Trigger 形式进判断器，准入走预先写定的规则（explicit），不占研判资源。

## 4. 组通道管道

组消息依次经过三级处理，才有资格成为候选：

1. **窗口化（Inline & Spill，按量触发）**：量大时才启用。进上下文的先压成卡片（限长），原文永在会话外、留指针按需取——热的内联、冷的溢出。研判窗口取法（参考实现）：线程头 5 条 + 触发前后各 5 条，长文截断并标注全长，其余给存根。个体通道不触发本级。
2. **Trigger 归一**：事件压成同一种**不可变 Trigger**（带来源、actor 等元数据）。Trigger 是审计与幂等的单位：同一事件收两次，只算一次。同线程串行处理，显式要求才并行。
3. **Gate（代码准入）**：核心条件一条——**是否 @ 它**。@ 了才有资格往下走；没 @ 的只记录、不动手（占最少注意力的第一道闸）。名单、强度（explicit / inferred / ignore）在此一并裁决；机器人与 CI 等机器来源单独走机器门（只认名单内、一律 inferred）。

过 Gate 的消息成为**候选卡（Candidate）**，进入评估队列。候选卡内容：触发原文卡、窗口上下文、所属线程已有工单清单、准入强度与依据、policy 版本。

## 5. 评估与工单

### 5.1 评估（Eval）全流程

```
候选卡 → 按 Thread 攒批 → Router 研判 → 代码复核 → 落 Decision →（接单）开工单
```

- **攒批**：同一 Thread 同时只跑一个评估批次。先剔除两类：已归某工单管的后续消息（那是订阅的活）、已开过工单的 Trigger（防重复开单）。
- **研判（Assessment，AI 的活）**：Router 读规则文件（prompts）对候选卡给四种处置之一——**接单 / 挂靠（attach 到已有工单）/ 停单 / 忽略**。判据：是否本域、是否有具体意图、方向是否已定；含糊的与纯讨论的静默忽略。研判全程只读。
- **复核（代码的活）**：AI 只有建议权，代码有否决权。inferred 的接单必须满足：当前模式为 auto、且研判引用的规则全部启用，否则驳回（notExplicit）。验过才落 Decision 并开工单。
- **超时与重评**：评估带截止时间，超时自动重排（最多 2 次），再超时标 unavailable 并挂起等人处理；规则（policy）变更时，在跑的评估全部重评。
- **退回（handback）**：Worker 发现某 Trigger 超出本工单范围，可退回重评，每工单每条限一次。

### 5.2 工单（Ticket）：带编制的任务列表

工单不是普通待办条目，每张单具备：

- **状态机**：开单 → 已分派 → 执行中 → 待确认（指交付前的 Router 验收 / 待用户就 Attention 决定，不设「已交付待确认」）→ 关闭。执行中可一句话修订；交付后不重开，用户一句话开**关联调整单**（见下）。
- **授权书（Mandate）**：开单时生成、不可变——policy 版本、授权范围、强度、命中的规则。执行恢复前复验，防旧授权被新规则架空。
- **目标与来源**：目标一句话；来源 Trigger 的 id 集合（顺链可溯）。
- **标题与活摘要**：标题开单时生成、基本不变（辅助模型生成，Router 兜底），供列表识别与通知引用；活摘要随目标、进展、卡点持续更新。两者也是新建查重的比对依据。
- **跟进处置与防重复**：跟进消息先处置、默认挂靠原单（补充/转向走修订，提问只答，超 Mandate 先确认）；新建前按标题+摘要查在办与刚关工单、代码卡关，同一 Trigger 只生一单，重复单可合并。交付后调整不开原单：新开关联调整单，链回原单、只写差异，Router 凭原单与结果包恢复上下文。
- **分派（Assignment）**：见 §5.3。
- **订阅（Subscription）**：见 §5.4。
- **处置账（Disposition）**：每个 Trigger 的评估与去向全程留痕，可审计。

### 5.3 分配权属

- **决策归 Router**：派给谁、何时派、优先级——需要全局视野，只有调度者能定。决定**写回工单**的 Assignment 字段。
- **投递归机械**：工单层只落册、不派活；Worker 池**凭单领活**，投递是记录驱动的机械动作。Router 是调度者，不是邮递员——它不亲自投递、不在线等投递结果，以此保护其上下文与注意力。

### 5.4 订阅

- 工单与线程多对多绑定。已开工单的线程，后续消息**直达工单、不过评估**（订阅直达）。
- 订阅带去的只有**上下文**，不带新权限——后续消息不能扩大工单的授权范围。

## 6. 主会话（Router）

### 6.1 定位与职责

- 面向用户的总助手与全局调度者：持续聊天、理解需求、直接回答，也负责读候选卡给处置、定分配、跟进工单、验收成果和组织交付。
- **来源明确**：主人一对一消息按 §3.2 直达 Router，保留原文与可信来源；群聊候选、执行结果分别以候选卡和结果包进入。原“不摸裸消息”指不能把未分流、无来源约束的消息流当作调度依据，不限制与用户正常聊天。
- **派工后自然回复**：创建工单成功后，由当前 Router 根据任务与对话自行组织回复，使用正常文本回答或 `assistant_reply`；不由程序插入固定接单句，不限定句式与长度。渠道接单沿用同次 Router 研判生成的回复，经准入复核后持久投递，不为确认再启动一轮模型。
- **不阻塞等待**：派活是异步的，Router 回复后继续可聊天；Worker 完成以新事件返回。主会话在两次事件之间是空闲，不是挂起（见 §12.3 判活）。受理不等于完成，最终交付仍须验收。
- **内置层目标**：平台级规则的提示词真源为 `plugins/superagent/prompts/builtin-layer.md`，应随插件发布，由 `engine.mjs` 作高优先级 section 装入，位于用户层上下文之前。当前文件已形成，运行时读取和发布清单尚未接线；引擎仍使用内联 section，不能声称该文件已生效。目标上用户文档链与内置层冲突时，以内置层为准。

### 6.2 Router 的手（协调工具边界）

（2026-11-04 口径更新，取代旧「带手阈值」：Router 不亲自执行，与现行实现及内置层提示词一致。）

- Router 只用**协调类工具**：查工单与状态、定时提醒、配置、记忆记账、验收与交付组织。用户当面要求记住、纠正、遗忘，由 Router 当场记账，不另开工单、不逐条审批（见 §11）；2026-11-04 记忆模块已按此解耦，来源、版本、纠正与遗忘保护继续有效。
- **一切环境操作一律开工单派 Worker**——查网站、查文件、写代码、跑命令、对外发送，即使一步能完、即使只读，也不例外。
- 简单问答与状态查询由 Router 直接回答，不开工单；那是信息处理，不是执行。
- 判断口径只一问：这是不是环境操作。是，就派工。

### 6.3 四个内置单元

主会话卡内含四个内置单元（不是独立模块，是主会话的组成部分）：

1. **辅助模型**（见 §7）
2. **Fallback**（见 §9）
3. **文档链路**（见 §10.1）：SOUL → IDENTITY → USER → AGENTS → MEMORY 一条链；治理规矩也在链上。
4. **账本层**（见 §10.2）：FTS5 原文检索 · Inline & Spill · 链式回忆。

## 7. 辅助模型

- **只定义一个**辅助模型，给它一份**能力清单**；杂活按能力路由给它，不按任务各配一条链。
- 能力清单做成**设置页的勾选项**：勾上才归它管，改设置即时生效，实现**动态分配**。典型能力：看图、压缩、总结、后台 review。
- 例：看图默认不归辅助模型（主流主模型自带看图）；换上不能看图的主模型时，去设置页把「看图」勾给辅助模型即可。
- 辅助模型走便宜档——前提是效果相当（见总原则 3）；效果有差，杂活也回主模型。
- 辅助模型自带备选名单，兜底单点。将来某类杂活高频到排队，再为该类单开槽位（架构上只是加一行配置）。

## 8. Worker 池

**Worker 的定义（对齐原文第四节）**：被 Router 派活、在隔离中干活的执行单元，隔离是三重的——**上下文隔离**（独立会话，只见自己的任务包，不背全局）、**环境隔离**（独立执行环境，工作区互不污染，因此才敢并行）、**状态外置**（它的可恢复状态经工单与账本承载，不仅留在自己进程里——存算分离在 Worker 侧的落点）。后续事件经订阅直达它（§5.4），结果回流 Router 验收。它不决定分派、不管全局，分派是 Router 的制度职责，不是它的临场发挥。


- **每个 Worker = 一个任务的执行者**，与并行 subagents 没有区别：领一张工单、开一个隔离会话、干完交结果即散。无长期身份、不养专长——经验与记忆长在文档链路与技能里，不在 Worker 身上。因此 Worker 可随便并行、随便换、失活后可读账核实并恢复（外部效果未知时不自动重放）。
- **任务包**（派活时的形态）：Inline 卡片 + 原文指针 + 验收标准 + 授权范围。上下文随单走，不随人走。
- **执行形态**：子代理会话为主；浏览器任务、定时任务、外聊 worker 为并列的异质执行入口，同归工单调度。
- **中途交接**：Worker 需要人拍板时，走结构化交接——问题**原样**递到提问人当初写消息的原地，不改写、不积压；这不算进度汇报，是 attention 请求。
- **检查点**：写文件、危险命令前自动打检查点（影子 git），事后可整回合回滚——与事前审批互补。
- **调度上限**：Router → Worker 池是 **♾ 并行调度**——♾ 是「架构不设限」的图标，实际并行上限在设置页可配（跟随供给额度与用户验收带宽调整）。同线程内仍守串行纪律。
- **结果包**（交活时的形态）：正文成果、干了什么、证据在哪、未尽事项，以及目标需要时的文件产物。纯文本/新闻摘要无需生成文件，checkpoint 的 0 文件不是失败条件。Router 对照本单目标验收，不临时增加产物要求；详见[任务结果验收矩阵](任务结果验收矩阵.md)。
- **验收后续**：本轮结果未通过不直接结束工单。可修复问题由 Router 自然说明原因并自动恢复原单、原会话和原成果继续；确需用户信息/权限/范围决定时，建立 Attention、回原来源提问，答复后原单续做。内部核验故障由系统补证/重试并告知状态，不把证据判断交给用户。停止、撤权、预算及未知效果的执行门始终有效。

### 8.1 子代理委派规则（照 Muse 规矩原样采用）

本节只管 **Worker 向下委派子代理（第 1 层）** 这一层，规则照 Muse 的 Subagents 规矩原样采用，只换角色名（Muse 的主会话 → BenchGo 的 Worker）；Router → Worker 仍是工单制度派工，不适用本节的「自主可选」。不另设倾向清单、阈值表。

1. **自主决定**：是否向下委派由 Worker 自主决定。长、多步、自成一体、派出去能让 Worker 腾出手的工作适合委派；简单、单步的活 Worker 自己做。Router 不预先指定委不委派。
2. **并行委派**：真正互相独立的子任务，在同一轮一次派多个、并行开工。给子代理的任务说明保持简短：要干的活、期望的结果、非显而易见的约束、以及它上下文里可能缺失的早先细节。子代理拿到的上下文是 Worker 任务包的切片 + 原文指针，不继承 Router 的开局包（此为本设计既定的传递对象口径，不随本节改变）。
3. **嵌套封顶一层**：Worker 就是扇出的协调者；子代理不得再派自己的子代理，嵌套到此为止。
4. **派出后撒手**：派出后 Worker 只在工单里简短记一笔，继续处理工单内的其他工作；不持续复述委派进度、不预测或编造结果、不轮询子代理状态——结果由运行时回送到 Worker。
5. **不因慢而关**：不得仅因表面缓慢或暂时无动静关闭子代理；只在需要替换其工作、重新分派或取消时才关闭。
6. **状态与失败处理**：被问及子代理进度时，只查一次并按观察到的状态回答（运行中 / 安静 / 完成 / 需注意）。子代理呈中断、失败或未知状态时，先检查它已有的产出，再决定上报 Router、重新分派或关闭；不得悄悄丢弃工作。
7. **不可逆动作**：重复执行不可逆动作之前，先确认该动作是否已经生效；一份失败报告不等于什么都没有发生；结果未知时不重做，并逐级上报。
8. **责任与交付**：子代理的结果只回 Worker；Worker 复核、整合后签发结果包。子代理不直接交付用户、不直接向用户提问，问题逐级上报（见执行中提问回路）。

## 9. Fallback 分层

顶不住往下退，退三样不同的东西：

1. **退 Key**：同供应商多 Key 凭据池轮换——模型没换，最便宜的退法；
2. **退模型**：角色/工作模型各自的 fallback 链（可跨供应商），按明确错误分类和有界策略切换。政策/权限拒绝不切换绕过；403 等状态不能脱离适配器分类一律当作凭据故障。换供应商时重解推理参数，保留完整对话语义和工具结果，不重放已发生的副作用；
3. **辅助模型备选**：辅助模型自己的备选名单。

语义：**turn 级切换**——每条新消息从本角色首选开始，回合内冻结配置，按已保存的有界备用顺序尝试，不无界横跳。显式选择优先，模型 ID 原样保存；切换范围、错误分类与实际请求须可追溯。

实现差距：现有代码已移除旧 `keyPools` 配置，只落实了首选/备用模型队列；这不代表删除架构图中密钥池的目标。后续优先复用基础层凭据与供应商路由服务落实该职责，不直接恢复旧字段或另造凭据库，见[开发清单](全链路对齐开发清单.md)。

与 RouterGo 网关的分工：网关管「供应商池内部怎么退」（服务端多线路优先级与探针降级），客户端 Fallback 管「整个网关不可用时退到哪」——两层同构、互为兜底。

## 10. 状态与记忆（双记忆）

记忆是两层，互补不替代：

| | 提炼层（文档链路） | 账本层 |
|---|---|---|
| 形态 | MD 文档：结论、拍板、偏好、人格 | 结构化账本：事件原文 + 关系图 |
| 比喻 | 长期记忆 | 工作记忆 / 证据库 |
| 用法 | 整份注入、靠理解 | 按 id 精确跳查、给原文 |
| 价值曲线 | 越老越值钱 | 工单结束价值骤降（审计期除外） |

### 10.1 提炼层：文档链路

| 文件 | 职责 |
|---|---|
| SOUL.md | 什么脾气：性格、表达方式、做事底线（人格宪法，最慢变） |
| IDENTITY.md | 对外是谁：名字、形象、标志 |
| USER.md | 主人是谁：名字、称呼、时区、在意的事 |
| AGENTS.md | 怎么做事：工作规矩、约定、踩过的坑；**治理规矩在此**（审批红线、渠道规矩、保险库使用规矩） |
| MEMORY.md | 记住的一切：拍板、偏好、关系、项目状态（另有每日日志做流水，定期提炼进来） |

- **冻结快照**：会话开始时将文档链冻结注入；人格、记忆、偏好中途写入只落盘，下个会话才进提示。快照管理解，不管许可：受控动作执行前读取磁盘现行规则，收紧立即作用于未执行动作，Worker 下个动作边界复验，放宽可迟，无法确认许可则 fail-closed。
- 写入只有 add / patch / remove 三种操作；超限报错、同回合内腾挪，不自动压缩改写。
- **写入时机（双记忆的关键）**：开局读入（冻结注入）、干活与输出时随时写回（即时）、事后 review 沉淀（见 §11）。三个口子齐了，记忆才是活的。
- **first-match**：项目规矩文件按候选名单定序加载，只认第一个命中的（.hermes.md → AGENTS.override.md → AGENTS.md → CLAUDE.md → .cursorrules 一类口径），保证一个项目一个规矩来源；SOUL 不参赛、恒占首位。同名文件沿目录层级为合并链，越深越优先。

### 10.2 账本层

- **会话原文检索**：全部会话存 SQLite + FTS5 倒排索引；检索返回消息**原文、不做摘要**（摘要会丢数字、记串话，原文是地面真相）；零 LLM 成本（约 20ms 是参考描述，BenchGo 待实测）。字面匹配（非语义）是对「查当时怎么说的」这一场景的正确取舍。
- **Inline & Spill**：见 §4 第 1 级——卡片进上下文、原文在外、凭编号取回。
- **链式回忆**：卡片带引用 id（Trigger ↔ Thread ↔ 工单 ↔ 处置账），回忆时顺 id 跳查。本质是 ID 绑定，与数据库主外键同理；链在写入时建好，回忆只是查账，确定、无损、零 LLM 成本。AI 只决定「顺链走多远」。
- Inline & Spill 与链式回忆是同一机制的两个面：前者管什么进上下文，后者管怎么找回去；没有链就不敢溢。

## 11. 积累与进化

- **后台 review 闭环（计数器触发）**：两个计数器——记忆按每 10 个用户 prompt、技能按单回合 10 次工具迭代计数；任一攒满即 fork 一个后台进程回放对话，一次办完记忆沉淀与技能沉淀，**与前台并行、不看忙闲**；沉淀走辅助模型（喂紧凑 digest，效果相当、成本低数倍）。
- **沉淀入口（同一流程、三个入口）**：① 显式指令（/learn，确定性保底——重要的事要有一条不依赖判断的通道）；② 提示词自然语言（用户说「把这套流程沉淀成技能」，系统识别意图走同一流程）；③ 计数器自动（review 闭环）。大语料走知识库模式：精益索引 + 按章蒸馏，不搬原文。
- **技能纪律**：技能文件标准节序（When to Use / Procedure / Pitfalls / Verification）；内容纪律——**教训不是日志**，只写可泛化规则 + 一句为什么，禁止事件叙事。
- **Curator 策展（重活挑闲时）**：自建技能按使用计数流转——久不用 → stale（14 天）→ 归档（30 天），永不自动删；合并前快照、可回滚，有审计账本；LLM 合并默认关。与 review 闭环分工：轻活计数器、重活挑闲时。
- **管理通道（直管制）**：沉淀产物不走人工确认；用户经设置页 CRUD 与对话直达（记住 / 纠正 / 遗忘）直接管理，变更留痕、可回滚；大范围删除先摆明影响范围，防手滑。
- **候选审核的含义**：图中的技能候选审核是质量、来源、去重与权限边界的系统审核，不默认要求用户逐条批准。当前记忆直写已落地，自建技能仍需人工批准是待对齐差距，不反向改成最终产品路线。
- 进化在本架构中是**后台机制**：以虚线挂在内置组上，不占主流程。

## 12. 治理

### 12.1 规矩部分（归文档链路，执行门兑现）

- **审批**：发消息、花钱、删东西等不可逆动作永远过人（审批卡）。红线写在文档链里，由执行层按磁盘现行版逐动作复验并复用宿主审批门，不依赖冻结提示中的旧许可。
- **渠道规矩**：每个外部会话一份规矩（什么能说、什么不能说、什么能办），按会话生效。
- **保险库使用规矩**：密钥不进聊天、不进记忆、不进日志——规矩归文档。

### 12.2 机制部分（归系统实现）

- **保险库机制**：密码、API Key、验证码只经保险库——用户在安全界面录入，**Agent 永远看不到明文**，用时由系统代填。这是全系统唯一「Agent 必须看不见」的东西，是地基。保险库存储仍加密，但不要求用户设置、输入或保存额外口令，也不提供手动锁定或闲置自动锁定；应用运行期间由保险库服务管理解密状态，退出后由宿主重新初始化。
- **保险库执行边界**：SuperAgent/Worker 只能提交凭据句柄和已绑定的目标，请求必须经过现行审批，并在发送前复验目标、方法和权限；服务只返回脱敏结果或状态，不返回明文。保险库不承担本机用户隔离，安全目标是防止 Agent、上下文、记忆和日志看到秘密。
- **Watchdog（治理层唯一的实时机制）**：住在内置组内，组内监督员。权责分明：
  - **主盯 Worker 池（有手）**：卡死、超时、异常——可重启、退回、报警，有处置权（Worker 是一次性的手，处置它没有顾虑）；
  - **兼看主会话（只有眼）**：活着时只有眼——测活、报警，不纠偏、不改派；确认失活后仅恢复存续，不代替其判断；
  - **兼看工单管道**：评估超时重排、工单久挂不推进，由它盯并升级。

### 12.3 判活方法（主会话「等 Worker」时如何判死活）

前提：主会话不阻塞等待（§6.1），故不存在「卡在等待里」。判活靠三本账：

1. **调度心跳**：事件循环 / 进程级心跳新鲜，证明调度器还转；
2. **在等明账**：每张开出的工单都登记执行者与截止时间——等的那方 Worker 心跳在跳，就是合法等待，等多久都没事；哪方心跳停了，故障就定位在哪方；
3. **截止时间**：研判、工单都带 deadline，超时自动升级（重排、unavailable、找人）。

兜底：状态全在工单、账本、文档里（存算分离）——主会话真死了，拉起新会话读账即可续上。Watchdog 对主会话的职责是**发现 + 重启**，不是抢救。

## 13. 输出与交付

- **输出组即终点**：成果经组总线进输出组，结果交付在此完成，不再外延。
- **分级交付**（见总原则 4）：没事不报、要报给结论 + 证据、要拍板才摆选项。
- **回来源渠道**：结果回到任务来源的对话里交付，不让用户去别处（面板、工单系统）翻找。
- **完成与沟通分开**：只有通过验收才把成果作为完成交付；验收失败、返工或阻塞也必须由 Router 在原来源说明原因与下一步。可修复失败说明后自动继续，真正阻塞告知并等待回答；不以固定模板限定 AI 表达，不把“未通过”当作静默的理由。
- **UI 变更类成果**须附前后对照的视觉证据（Before + After），只有改后图算不完整交付。

## 14. 任务的一生（全流程）

以下为组通道流程；主人一对一仍完成来源分类和 Trigger 留痕，跳过群聊窗口、Gate 与是否接单的 Eval，进入 Router 需求理解和分诊，必要时从工单步骤继续：

1. **事件**：消息到达某渠道；
2. **分类**：判断器定性——组 / 个体（§3）；
3. **归一与准入**（组）：窗口化 → Trigger → Gate 看是否 @（§4）；
4. **候选卡**：打包送入评估队列（§4）；
5. **研判与复核**：Router 四处置、代码复核、落 Decision（§5.1）；
6. **工单**：接单生成工单 + 授权书，Router 写回分配（§5.2 / §5.3）；
7. **执行**：环境操作一律由 Worker 凭单领活、按任务包执行，Router 保持协调（§6.2 / §8）；中途提问走交接、不可逆动作走审批、状态被 Watchdog 盯着（§12.2）；
8. **验收**：Worker 交结果包，Router 对照工单验收、核销（§8）；
9. **交付**：经输出组分级交付回来源渠道（§13）；
10. **沉淀**：计数器推进，后台 review 把本单的教训沉淀进文档链路与技能（§11）；全程原文进账本，可 FTS5 检索、可顺链追溯（§10.2）。

任务一生的五种形态：**候选卡 → 处置 → 工单 → 任务包 → 结果包**（外加最终的分级交付）。定时任务在第 1 步由定时器合成事件，其余同路。

| 投机执行的内部策略验证 | 「静默复现并修复」：确认问题存在且修复简单才交付，否则全程安静 | 主动有界 + 交付门槛后置（基础特征·主动、§13） | 已吸收 |
| 实验边界（原文自陈） | 只验证了**调度时延**，未验证产出质量；场景为其内部仓库 + 用户群，约 300 条消息 × 5 轮 | —— | 提醒项：上述数字只作**方向证据**，不作本设计的性能预期；质量维度本设计另靠验收与分级交付兜底（§8 / §13） |

旧版 Router 带手阈值已由 2026-11-04 的 §6.2 废止：环境操作均委派 Worker；普通问答与协调不创建执行任务。不得再将旧阈值作为现行架构或运行许可。

## 19. BenchGo 落地口径（2026-11-02 会话确认）

本节与专题文档是作者原稿的落地补充；2026-11-04 已更新条款及 §20 优先于本节旧措辞。旧引用 `BenchGo-SuperAgent设计.md` 当前工作区不存在，来源边界见[参考核对](参考核对.md)，不将缺失原稿作为可访问证据，也不由参考仓库反向定义产品。

### 19.1 范围与权威

先在一台 BenchGo 上跑通，首轮包含完整 Trigger / Gate / Eval / Ticket / Subscription，群聊入口使用飞书。桌面主人一对一与飞书群聊共用同一个编排与账本，不以多设备部署、多 Profile、微信接入作为前置条件。飞书具体授权范围、机器人身份与接入配置在实施时绑定，不在文档中虚构已连接状态。

SuperAgent 管编排、授权快照、工单、分派、订阅、验收、交付和进化；Harness 管会话、执行及官方服务。复用已有 Schedule、skills、审批、凭据和运行时，不复制推理循环或 Cron 调度。RouterGo 是模型供给方向，不是本仓库新建的网关实现。

### 19.2 三项已裁决语义

- 主人一对一保留全文，跳过群聊窗口与 Eval 的“接不接单”裁决；仍分类、登记不可变 Trigger、去重留痕、由 Router 理解需求，环境操作开工单。普通问答、定时协调与用户当面的记忆记账不强行建单，配置等其他受控动作保留各自授权契约。原文进入结构化信封，因此“直通”与“不摸裸消息”兼容；不将问句解释为外部操作授权。
- 冻结快照管理解，不管许可。人格、记忆、偏好下个会话生效；每个受控动作执行前读取磁盘现行规则并复验权限。收紧立即作用于尚未执行的动作，运行 Worker 在下个动作边界停下来复验；已完成副作用不能撤回。放宽可立即生效，但不要求模型立刻刷新快照，始终 fail-closed；规则不可读或版本无法确认时不执行受控动作。
- Watchdog 对活着的 Router 只有眼，不纠偏、不改派、不代决策；对确认失活的 Router 才有恢复存续的手，通过宿主拉起进程或新会话，让其读账自主续上。先排除旧写入者仍活着；外部效果未知先核实。心跳、请求 deadline、工单 deadline 分别记录，合法异步等待不是失活。

## 20. 现行架构口径与实施顺序（2026-11-04）

先完成 SuperAgent 主聊天，项目聊天押后。保留官方会话、输入容器和渲染组件，QuietChat 只投影用户消息、正式回复、已验收交付和待处理交互；交付正文与正式回复一样呈现为普通助手消息，不再单列「交付通知」卡片、分类标题或「标记已读」入口。需要用户决定的问题保留必要选项和审批语义；来源归属、版本、去重与交付账本继续保留。进展与执行过程进入工单和看板。不新建会话系统、推理循环或平行任务队列。

消息工具栏固定在正文左右两侧，通过正文最大宽度保证操作空间，不因悬停或容器变窄移到底部；隐藏和显示不改变消息间距。具体约束见[消息工具栏与回应](消息工具栏与回应.md)。

- 入口是高低噪声的唯一分支点，之后复用工单/执行/验收/交付；直通档跳过接单审查，不跳过 Trigger 留痕和实际动作授权。
- 新候选主要有 accept/answer/ask/ignore 四类结局；已有工单跟进的挂靠、停止、版本化修订是独立处置。定时纯提醒允许 answer，经直接回复送回原会话；执行型定时任务仍开工单。
- Router 无手；不相关的新请求独立分诊，干活类查重后并行派工。工单应有稳定标题和活摘要，交付后问题新建关联调整单，原单关账不回改。
- 开局包只给 Router：系统指令、运行信息、五文件全文、对齐总结、关系索引、活跃目标、能力目录、保险库清单、其他对话摘要、本会话窗口。Worker 只拿任务包，子代理只拿切片与原文指针；目录/索引不夹带正文。
- 记忆与学习按 §11 直管制：当面记账不另开工单，后台按计数器自动沉淀，事后可查看来源、纠正、遗忘和回滚；外部不可逆动作的授权审批不属于这一豁免。
- 当前五包单安装、官方执行、Goal 投影和记忆直写已有实现；内置层、上下文裁剪、工单身份/查重、失败续做、阻塞恢复、技能直管等缺口以[现状](现状.md)与[首版验收缺口](首版验收缺口.md)为准。定时/Voice 代码接通不等于运行实例已加载，也不代表真实端到端验收完成。
