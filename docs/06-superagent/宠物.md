设计日期：2026-11-03；源码校对：2026-11-04。状态：**应用内形象编辑与基准表情切换已实现；聊天动作接线仍有缺口，桌面与参考图编辑仍为规划**。以下现状按当前工作树核对；其余章节保留目标设计，不代表全部上线。

### 当前实现与历史验证

- 入口：SuperAgent → 资源 → 身份 → 形象；首页与聊天复用同一角色，侧栏显示同一身份入口。默认无名，姓名归 IDENTITY.md，主人档案为 USER.md，人设为 SOUL.md，继续使用原有记忆、会话和 Router。已有自定义 HTML 名片优先显示，应用宠物形象不会替换它。
- 基准创作：复用 21 个表情、11 个装饰、6 个配色与受控组合规则；保留正式品牌母版的身体和编辑器特征，运行时不依赖 VI 项目。
- 个性化：上传 PNG/JPEG/WebP 主图与自有表情；先预览，再应用，可取消、恢复上一版或默认。替换主图清除旧表情绑定，换外观不修改身份、记忆、模型和权限。
- 对话：复用现有输入框与图像生成工具，`assistant_pet` 提供查询、预览、应用、恢复和短表情；模型写入沿用现有审批与工单。聊天显示待应用草稿，基准角色根据运行/待确认状态切换表情，不把回复结束当作任务成功。
- 动作边界：共享组件已有点头、侧倾、轻跃、摇摆四种短 CSS 动作，形象页可预览；当前聊天通过 `AssistantCard` 展示形象，其内部 `PetAvatar` 固定 `motion={false}`，没有接入计算出的 action。原创角色的短表情也未从聊天状态传入图片选择，不能宣称已完成聊天自动动作及原创短表情展示。
- 性能与资源：不为动作单独调用模型；共享动作组件遵循减少动态效果与页面可见性。图片限 8 MiB、单边不超过 8192 像素、总像素不超过 32 × 1024 × 1024；实际解码后转静态 PNG、去除元数据，并拒绝多帧图片。资源路径与配置版本均校验。
- 尚未实现：桌面悬浮窗口、原创图参考编辑/局部换装、骨骼动画、头像裁切、主图损坏时自动回退上一版、验收成功到完成动作的自动映射。现有图像服务只生成新图，不保证原创角色换装一致性；不展示无效桌面开关。图片加载失败显示“形象不可用”，上一版需用户在形象页手动恢复。

## 1. 评估结论与产品定位

上一版个性化方向正确，但存在两处偏差：一是把静态上传作为核心交付、把动作推迟，容易做成头像编辑；二是提前安排创作工作室、三页设置、历史管理、挂点系统与桌面聊天面板，成本偏高。应同时修正：**保留角色的表现力，减少围绕角色建立的系统。**

**产品与品牌始终叫 BenchGo，默认宠物没有名字，由用户自行决定是否命名。** 用户指定的品牌 VI 项目是设计参考源；其项目名不作为宠物名称，也不出现在宠物面向用户的文案中。默认形象采用 BenchGo 正式素材，个人形象可以从基准修改，也可以完全原创；应用图标、安装器和托盘品牌不随个人宠物改变。

SuperAgent 本身就是宠物助手，承担面向用户的 Router 职责：用户可以直接说“我要一只怎样的宠物”“换一件衣服”“换个表情”，它也会随聊天与真实工作状态做出适当回应。形象、表情与动作形成统一的角色体验，不另建 Agent、模型会话、任务系统或人格档案。

轻量的原则是：**创作时按需生成，使用时复用素材；已有事件决定工作状态，当前对话可附带轻量表达意图，本地规则负责播放。** 不为每次眨眼、回应或任务进展调用生成模型。

### 范围取舍

| 保留的价值 | 收紧的实现 |
| --- | --- |
| 对话创造、换装、改表情 | 复用现有聊天与图像能力，不另建创作工作室和模型选择器 |
| 有表情、有动作、有回应 | 可复用动作库与本地播放规则，不做实时视频生成或复杂情绪引擎 |
| 个性化与完全原创 | 上传和生成均可用；不强制原创角色长成品牌吉祥物 |
| 预览、应用、恢复 | 当前版本、上一有效版本、一个待确认结果，不做完整历史管理产品 |
| 桌面陪伴 | 单角色轻窗口，点击回现有聊天；不复制输入框、任务中心和通知系统 |
| 配饰变化 | 基准角色优先调用现有装饰组合能力，原创角色按需编辑；不重复建设挂点、碰撞和衣服商城 |

## 2. 现状与品牌基准

### 已有与待做

- 已有：助手姓名、默认 BenchGo 名片、受限 HTML 名片、轻动效、配置 revision 同步，以及 SuperAgent 对话与任务服务。
- 已有：个人图像资源、对话创作引导、表情目录与形象页短动作预览、聊天基准表情的运行/等待状态映射；聊天动作与原创表情接线、桌面宠物窗口及更完整事件映射待做。
- 不能假定已有：图像服务一定支持参考图或局部编辑、桌面宿主一定支持透明窗口、现有品牌素材已包含眨眼或其他表情。

现有“没有名字的助理”是存储默认文案，新的宠物界面不将它当作宠物名字。已有助手姓名保留，不凭字符串批量清空。宠物与助手是同一身份，名字统一由 IDENTITY.md 管理，不另设宠物昵称；主人档案与宠物档案的归类见第 8 节。

### VI 如何使用

默认形象的运行与构建来源仍为 `assets/brand/`，不依赖 品牌 VI 项目的本机路径或外部网页。VI 参考版本见文末。

- 正式基准：暖米白 `#F3EBDF`、朱红 `#D44A36`、深墨 `#222222`、暖灰 `#B6B1A7`，背景浅灰绿 `#E8EAE5`。
- 保留正式母版的身体、双眼、切角、编辑器特征与比例，不通过拉伸适配场景。小头像使用认可的简化素材或合适裁切。
- 官方默认表情必须另做认可的角色衍生素材，不能把现有母版“可整体浮动”描述成“已经会眨眼”。个人换装和原创结果存为用户资产，不回写品牌母版。
- 完全原创可改变物种、轮廓、颜色、画风与面部结构。统一的是清晰度、交互和状态语义，不要求所有角色有双眼、有嘴或有人形身体。
- 基准角色复用 VI 项目已有组合、挂点与校验，不重新实现一套；不同画布与 BenchGo 编辑器特征的适配仍需验证。原创角色不强行使用基准挂点。

## 3. 用户主要通过对话创造自己的宠物

### 一个入口，不增加一个创作产品

沿用 **SuperAgent → 身份**，增加简洁宠物区域：当前预览、可选姓名、换形象、动态开关、恢复上一版/默认。换形象提供“上传图片”和“让 AI 帮我设计”；后者进入现有聊天并带入当前角色引用。桌面能力上线后再增加显示开关。

聊天是主要创作界面，设置页是查看和管理入口。无须先理解素材类型、模型参数、坐标或动画格式。生成服务默认复用现有明确选择；只有缺少配置或能力不支持时，才展示原因与现有配置入口。

### 四个核心场景

| 用户表达 | 系统行为 | 用户确认的结果 |
| --- | --- | --- |
| “给我做一只安静的机械水母” | 生成一张主形象；无生成能力则说明并提供上传路径 | 在聊天中预览完整角色和小尺寸效果，应用后替换 |
| “给它换一件黄色雨衣” | 先查当前角色兼容的装饰目录；已有雨衣则组合，没有时以当前角色为参考生成穿搭版本 | 前后对比，继续修改或应用；不用用户管理衣服图层 |
| “换个开心的表情” | 已有兼容开心素材则短暂展示；基准角色先查现有目录，确实缺少时才生成候选表情 | 确认后保存并播放，以后可以复用 |
| “以后默认就用这个表情” | 将选定的有效表情设为默认姿态 | 明确改变默认，保留恢复入口 |

“看起来更开心一点”若是在编辑候选图，则修改该候选；在普通聊天中则优先作为一次表达。只有不清楚用户是要暂时表现还是永久修改，且上下文无法判断时才简短询问。

### 创作闭环

1. 读取当前形象作为参考；用户要完全原创时允许从空白开始。
2. 核实实际服务是否支持生成、参考图、局部编辑，原样使用模型 ID；不支持时不能假装做了局部修改。
3. 已有素材能够满足时直接组合预览；确需生成时默认生成 **1 个结果**，用户要求才增加候选。显示生成状态与已知消耗信息，失败保留描述和参考图。
4. 在当前聊天中显示“应用 / 继续修改”；可展开完整角色、小头像与浅深背景预览，不再打开专门工作室。
5. 应用时一并更新角色引用和相关表现资源，成功后各位置刷新；失败保留当前形象。
6. 保留上一有效版本用于恢复。未应用结果依托现有聊天产物保存，不建立多草稿和历史版本管理页面。

生成后对照轮廓、主要配色、标志性特征和画风。模型不能保证身份一致，因此换衣服不应悄悄把角色换成另一只。用户可以继续修正；没有满足需求之前保持原形象。

上传自己的画作也是完整个性化路径：支持 PNG/WebP/JPEG，默认等比完整展示，头像裁切按需调整。无需强制透明背景、强制取名或先制作全套动作。远程去背景须明确告知上传行为；无相应能力仍能使用原图。

## 4. 表情与动作库：这是角色能力的核心

### 分开管理两个概念

- **表情/姿态素材**：角色看起来如何，例如平静、开心、好奇、专注。同一表情可用于不同动作。
- **动作配方**：角色怎样表现，例如轻点头、微倾身、短浮动、一次庆祝。优先用本地 transform/opacity 与素材切换组合，不需要每个动作一段视频。

将二者分开后，一张原创图也能先有回应动作；增加一张开心表情就能改善多种互动。不需要为每件衣服生成“表情 × 动作 × 场景”的全排列。

### 首版的动作库

下表是表现语义，实施时映射为受控动作 ID，不改变现有后端协议。默认形象需提供经确认的基础素材，原创形象缺少某项时按规则降级。

| 动作 | 触发 | 素材需求与表现 | 播放策略 |
| --- | --- | --- | --- |
| 待机 | 没有更高优先级动作 | 默认姿态；有素材可偶尔眨眼，否则保持安静 | 可见时低频，默认无持续大幅浮动 |
| 回应 | 用户提交消息、主动轻触 | 整体轻点头或倾身，不强行变形 | 单次，合并短时间重复事件 |
| 专注 | 当前会话确实在执行 | 默认或专注姿态，轻微姿态变化，文字沿用真实状态 | 开始时短播；长任务静止，不无限抖动 |
| 开心 | 普通对话的合适回应 | 开心表情配轻抬起；没有表情时仅轻动作 | 单次，不解释为任务已完成 |
| 完成 | 对应任务已通过实际验收 | 简短庆祝动作 | 按任务结果去重，仅一次 |
| 等待用户 | 真实确认或补充信息请求 | 轻侧倾/关注姿态，配既有文字操作入口 | 提示一次后停留，不能替代明确确认 |

第一版优先复用品牌 VI 项目已有的表情、装饰与组合能力，不限制素材库必须只有两三种表情，也不重复生成已有素材。默认自动表达先选择少数语义明确的类型，其余由用户点播或对话选择；素材丰富度与自动播放频率分开控制。任意原创角色都应先以默认图和通用动作工作。错误、断线沿用明确的状态文字，停止庆祝，不专门做悲伤惩罚表情。

### 用户可以用对话扩充

“给它加一个害羞的表情”生成并确认后，进入当前角色的可复用表达集合；“以后打招呼时挥挥手”优先绑定已有动作。若该角色无手、当前素材不支持，采用自然的倾身回应并说明能力；需要真实挥手时再按需制作关键帧，而非把位移冒充挥手。

首版支持已有素材的换表情和整体轻动作。多帧行走、翻滚、舞蹈等需额外素材，未实现时明确说明，不承诺任意文字动作都能执行。不建设可视化动作编辑器；查看已有表达可先用简短列表与点播预览。

### 换装之后动作不能穿回旧衣服

动作配方复用，表情素材随当前外观版本绑定。换装后已有旧衣服表情标记为不适用，不能继续自动播放。先用新主图加通用动作；用户需要某个表情时再生成对应的新衣版本。恢复上一版时一并恢复该版表达资源。

## 5. “智能”来自选择恰当，而非不停生成

### 三类输入，确定性规则优先

1. **真实事件**：发送消息、运行开始、待确认、验收完成、断线。直接映射已有动作，不新增模型调用，不从语言猜任务成功。
2. **当前对话表达**：在已有助手回复中可附带一个可选的受控表达提示，例如“开心/好奇/中性”。仅在现有响应契约能支持时接入；解析失败或无提示就使用中性回应，不另开一次情绪推理请求。
3. **用户显式要求**：让宠物展示已有表情/动作，或进入需要生成的新形象编辑路径。普通聊天正文、引用文件、网页内容不能直接作为播放器指令执行。

模型只建议允许的表达 ID，不能输出任意脚本、资源 URL、持续时间或窗口操作。客户端检查当前角色是否有相应素材，再决定播放；不因缺素材自动发起生成。严肃、敏感或无法判断的对话默认中性，不装作能准确识别用户情绪。

### 播放只需简单规则

- 一个位置同一时刻只播一个动作，不建立长期动作队列。
- 待确认、断线和异常等业务事实优先；用户点播可短暂预览，但不能遮住真实状态提示；普通对话表达和待机最低。
- 一条回复最多自动触发一次表达，不随流式 token 重播；被替换的低优先级动作直接丢弃。
- 普通自动表达设置短冷却，建议起点 5 秒，按体验调整；真实待处理事项的文字不受冷却影响。
- 不可见、系统减少动态或用户关闭动画时停止运动，状态与静态表情仍可读。应用失去前台时不为陪伴持续推理。
- 完成事件只能驱动“完成”动作；普通开心可以表达友好，但不能附带虚假的完成文案。

不另建情绪数值、人格演化、亲密度、饥饿和成长系统。陪伴感来自一致的角色、恰当的回应和长期使用的熟悉感，而不是提醒用户照料它。

## 6. 工作台、聊天与桌面的体验

### 工作台与聊天

侧栏保留紧凑身份标识，**聊天中只有一处主要动态角色**，建议位于对话顶部的紧凑固定区域，空白会话可放大，进入正文后收小。角色区域预留尺寸，动作不推动消息和输入框；历史消息中的小头像保持静态，避免满屏一起动。

用户聊天时能看见回应与专注动作；表情不遮挡回复、引用、复制和输入。点击主要角色打开简短操作：编辑形象、查看可用表达、动态开关。名字可为空，消息作者仍有清楚的角色标签。

外观创作结果直接出现在聊天里，用户不必在多个界面往返。需要确认的工作仍在既有业务组件完成，点击、抚摸宠物不能批准工具操作。语音沿用 Voice，宠物不新增监听；没有口型素材时使用播放状态，不凭空长出嘴巴。

### 桌面：保留陪伴目标，先做最小可用形态

默认关闭，使用同一角色与动作库。开启后提供拖动、点击打开现有 SuperAgent 对话、隐藏与恢复。位置按设备保存，换屏/DPI 变化后保持可见；关闭桌宠不停止任务，退出 BenchGo 默认一并退出。

首版不另造桌面聊天面板，不加文件拖入、游走、追鼠标、独立通知气泡、可配置快捷键体系。桌面模式能提供安静待机和真实事件短反馈即可；已有系统通知继续承担通知，不增加宠物跨设备提醒协调系统。

必须先验证自有桌面包装层的正式扩展点支持透明窗、合理命中区域、焦点与多屏管理。不能修改官方子模块或恢复 runtime patches；透明留白不应挡住其他软件操作，不抢焦点，恢复入口始终可达。不满足时明确暂不支持桌面，应用内体验独立完整。

### 多端一致与不过度曝光

同一授权范围复用当前形象与表达资源，设备位置和桌面开关不跨设备同步。聊天在前台时由聊天主角色播放，桌面宠物不重复庆祝；桌面主要在应用后台承担轻反馈。首版只做本设备可见性判断，不建设跨设备唯一播放协议。

Link 移动端复用静态头像与一处轻动作展示，不做系统级悬浮窗。所有入口可点击和键盘操作，不依赖悬停。关闭宠物仍能使用全部助手功能。

## 7. 最小实现与质量边界

### 实现构成

只增加必要部分：**既有助手档案中的外观配置、角色资源引用、受控表达清单、共享展示组件、状态到动作的简单映射**。配置放 SuperAgent；公共资源/提供商能力和 UI 复用已有 BenchGo 与共享组件。继续只安装一个 `benchgo-plugin`。

- 当前角色记录主图、头像裁切、当前可用表情引用；动作配方使用共享定义，不为每位用户复制代码。
- 默认素材和用户素材分别保存；用户数据不进入 `assets/brand/` 或源码树。
- 沿用配置 revision 和差异保存；新资源验证成功后再切换当前引用，旧响应不能覆盖新配置，保留一个上一有效版本。
- 未应用结果复用已有聊天产物能力；宠物档案就是既有助手档案，外观数据只补必要结构，不提前创建专用数据库和生成任务队列。
- 真实任务状态复用现有订阅，不增加宠物专属轮询、状态存储或业务执行入口。
- 生成调用走现有授权与任务路径；局部编辑、透明输出等能力分别检查，工具名和模型 ID 不猜测改写。
- `cardHtml` 保留，用户选择改用宠物时才切换；不开放现有 iframe 脚本和网络能力。动态开关复用/兼容 `cardMotion`，不提供两个互相冲突的开关。

### 效果优先优化这些细节

1. 默认角色与适配后的现有表情画风一致、比例稳定；表情清楚，不能以数量代替质量。
2. 角色等比显示，头像能调整取景；24–32px 仍可辨认，非人形不被强制裁成人脸。
3. 短动作有自然起止，不每次大幅弹跳；同类事件反馈一致，阅读时不干扰。
4. 换装保持身份，新衣版本不会混入旧衣表情；原创角色缺素材时也有合适的通用回应。
5. 全部应用失败都保留当前有效形象；重载后外观与配置一致，不静默重置助手姓名、模型或记忆。

### 必须保留的工程约束

图像检查实际格式、体积与解码像素，不执行用户 SVG/HTML/脚本或外链动画；当前上限为 8 MiB、单边 8192 像素、总像素 32 × 1024 × 1024。缺少表情回退当前角色主图，不变回品牌角色。当前主图加载失败显示中性占位并保留配置，用户可在形象页恢复上一版；自动尝试上一有效图属于待实现优化。

使用缩略图、缓存和 transform/opacity，避免逐帧布局和每次事件重新解码。不同窗口可共享磁盘/网络缓存，不承诺跨进程共用解码内存。首版不引入 WebGL、Live2D、VRM 或重型动画运行时。

真实文字状态、键盘入口、系统减少动态、焦点与多屏恢复是必要质量要求，不能为了轻量省去。性能通过“开启/关闭宠物”的 CPU、内存、输入响应对比验证；静态展示与本地动作不产生模型调用，隐藏后无持续动画循环。此处均为待验证目标。

## 8. 统一身份：两类档案、一套记忆、一个助手

### SuperAgent 就是宠物助手，承担 Router 职责

产品上只有一个持续存在的助手：**宠物 = SuperAgent = 面向用户的 Router 助手**。它理解主人、交流陪伴、记住共同经历、协调项目与任务；形象、声音、表情和动作是它表达自己的方式。桌面、工作台和聊天是同一个助手的不同出现位置。

不提供独立宠物身份、宠物昵称、角色切换列表或另一个陪伴 Agent。用户可以把外观从基准形象改成猫、水母或完全原创形象，仍是同一个助手，名字、人格、记忆、会话和任务继续保留。用户明确要求修改名字或人设时，才修改相应档案；修改外观不隐含修改性格。

技术上仍分工：Router 处理推理与调度，渲染组件播放表情和动作，Harness 执行受控工作。这是同一个助手的内部职责分离，不是多个身份。关闭桌面展示或动画不会关闭助手、终止工作或抹去记忆。

### 两类档案：主人档案与宠物档案

这是面向用户的两种档案归类，不要求把现有存储硬合成两个文件，也不再创建重复的数据源。

| 产品归类 | 内容 | 既有权威与存储 |
| --- | --- | --- |
| 主人档案 | 使用者的称呼、时区、偏好、习惯、关心事项和协作需求 | 以 USER.md 为主；具体经历保留在统一记忆和会话账本 |
| 宠物档案：身份 | 助手的名字、对外身份、形象描述和标志 | IDENTITY.md；默认无名字，config.name 仅保留现有兼容回退职责 |
| 宠物档案：人设 | 性格、表达方式、行为倾向与底线 | SOUL.md；经过现有受控编辑流程修改，不根据一张新图片自行推断 |
| 宠物档案：外观与表达 | 当前形象、上一有效外观、头像取景、素材来源版本、表情/动作映射、兼容装饰 | SuperAgent 现有配置/资源存储中的最小结构；不复制姓名和人格 |

界面可按“主人档案 / 我的档案”呈现；“我的档案”就是宠物助手自己的身份、人设和形象。准确名称可沿用当前产品界面，但不能再出现一套独立宠物资料与一套助手资料。

“给你取名”“给宠物取名”“助手以后叫某某”在明确指向当前助手时，统一通过现有 assistant_config → IDENTITY.md 路径处理。未命名时使用“未命名”等界面占位，不把 BenchGo 品牌名或参考项目名当作用户给助手取的名字；已有用户名字保留。

外观资源只需保留当前与上一有效版本。资源 ID 是文件/版本标识，不是另一只宠物的身份 ID。位置、大小与桌面是否显示按设备保存，不进入人格文件。

### 一套记忆：就是宠物助手的连续记忆

SuperAgent 的记忆就是宠物助手的记忆，直接复用 MEMORY.md、会话记录、每日日志和既有任务账本，不创建 PET_MEMORY.md、陪伴记忆库或独立宠物日志。

记忆包括对主人的了解、主人与助手共同经历、明确的决定与承诺、任务结果、项目经验，以及值得长期保留的偏好。它不仅记录宠物外观，也支撑工作助手的连续性。“主人档案”是稳定认识的整理，“记忆”是可追溯经历与经验的积累；应引用和提炼，不在两处无差别复制。

| 发生的事情 | 保存方式 |
| --- | --- |
| “我一般晚上工作，别主动打扰” | 通过既有流程更新主人偏好；有实际通知开关则同步对应配置，不能只记一句话就宣称已生效 |
| “你以后叫某某，讲话温和一点” | 分别更新同一助手的 IDENTITY.md 与 SOUL.md，不创建角色 |
| “给你换一件雨衣” | 更新当前外观配置；现有聊天保留过程，不必自动追加长期记忆 |
| “记住，我喜欢这个造型” | 经既有记忆准入流程保留偏好与必要资源引用，不重复存图像数据 |
| 完成一次项目、作出一个长期决定 | 沿用任务证据与记忆提炼机制，不另写一份宠物经历 |
| 点头、眨眼、一次开心动作 | 不写长期记忆，不产生独立日记或模型调用 |

换形象、恢复默认外观、关闭桌面展示均不清空记忆；忘记或删除信息仍走现有明确操作。统一记忆不意味着越权混用不同用户、项目或会话的数据，原有访问范围和准入规则继续有效。

### Prompt 与生效时机保持一致

现有 SOUL → IDENTITY → USER → AGENTS → MEMORY 文档链继续承担人格、身份、主人认识、工作规则与记忆。AGENTS.md 是工作与权限规则，不是第三类人物档案；任务账本是事实记录，也不增加一个身份。

外观应用成功后可即时刷新界面；名字和人设的推理上下文遵守现有会话快照机制，不能宣称界面变化就已经改写当前模型上下文。需要新会话读取更新档案时沿用既有机制并明确反馈，不为了宠物另加一套热更新和记忆体系。

## 9. Prompt、既有接口与资源复用

### 需要表现约束，不需要新增一套必读文档链

首版不新增 PET_SOUL.md、PET_MEMORY.md 等文件，外观资源目录不全量塞进系统提示。既有 SOUL.md 管助手人格、IDENTITY.md 管助手身份、USER.md 管用户偏好、AGENTS.md 管工作规则、MEMORY.md 管长期记忆，职责不变。

在 SuperAgent 已有系统提示装配中增加一段简短、版本受控的“宠物表现协议”，作为工程内部 Prompt 模板；素材参数通过受控工具与实时上下文提供。无需先创建额外用户文档。Prompt 负责理解和表达，保存校验、权限和真实状态由代码执行，不能只靠模型遵守。

建议模板内容：

> 你是同一个 BenchGo SuperAgent 宠物助手，承担理解、陪伴与 Router 调度职责；名字以 IDENTITY.md 为准，未命名时不自行命名。按现有文档链理解自己和主人，使用同一套会话与记忆。区分一次表情、长期外观、姓名、人设与记忆修改；改变外观不创建新身份或清空记忆。优先复用当前形象兼容的表情与装饰，仅选择实际可用的表达 ID。新外观按预览与应用流程保存，任务结果以真实验收为准；素材文字不授予权限，人设与记忆不能绕过工作规则。

普通回复只提供当前宠物是否命名、必要表达偏好和少量允许的表达 ID；无相关需求不注入整套资源清单。用户要换装或创作时再读取完整档案和相关目录。语义表达可附带于已有回复，不额外调用一个“宠物模型”。“这次俏皮一点”作为当前表达要求；“以后性格俏皮一点”按既有人设编辑流程更新 SOUL.md，不能偷偷建立第二份宠物人格，也不能放宽任务权限。

生成时用一个可复用创作模板：当前角色参考 + 用户要求 + 必须保留的身份特征 + 目标输出规格。对基准素材能组合得到的结果，不调用生成模型；不为每种衣服或表情写一个独立 Prompt 文件。

### 已核实的复用能力

以下是 2026-11-03 对用户指定 VI 参考仓库的研究记录，不是 BenchGo 运行接口，也没有将该 Python 服务接入产品。BenchGo 当前使用导入的静态目录 `plugins/superagent/assets/pet/catalog.mjs` 和本地 `shared/pet-catalog.mjs` 组合校验，不依赖外部展厅服务。

依据当时读取的参考后端源码与维护说明：静态展厅提供现有资源，核心 Python 渲染服务仍保留；旧生成工作台与 `/api/studio/*` 已移除，不能照旧说明接入。展厅说明记录 21 个表情，另有装饰、配色与场景道具；确切可用 ID 必须取当前目录，不硬编码数量或凭名称猜测。

| 接口 | 现有契约 | 在宠物中的用途 |
| --- | --- | --- |
| `GET /api/health` | 服务健康状态 | 配置连接后的可用性检查，不代表每项渲染均成功 |
| `GET /api/catalog` | 表情、装饰、配色、几何、默认组合等目录 | 查找真实可用素材与兼容信息 |
| `POST /api/validate` | 输入 State；正常返回 warnings，非法 ID/部分非法组合可返回 422 | 复用现有保护区、挂点、对比度等校验 |
| `POST /api/compose` | State → SVG | 预览现有表情、装饰与配色组合 |
| `POST /api/export?format=png&size=512` | State → SVG/PNG；size 支持 240/512/1024 | 将确认结果固化为本地角色资源 |
| `POST /api/random` | 返回可编辑 State | 用户明确要求“随机来一个”时使用 |
| `GET /api/avatar/{format}` | svg/png；可带 seed、size 32–1024 | 生成初始候选；应用后保存文件，不持续依赖随机 URL |

State 包含 `expression`、`decorations` 列表和 `palette` 对象；palette 含 body/corner/ink/accent/scene/blush/fluid/panel 等色值，不能仅传一个色板名称。ID 原样使用。目录在服务启动时会合入提取表情、场景装饰及修整逻辑，不能仅复制源 catalog.json 就认为得到完整服务目录。

`validate` 的 warnings 不等于校验已全部通过，组合与导出也要检查实际响应。随机种子只能在对应素材与规则版本内稳定；长期外观通过保存 State、来源版本与导出文件固定。SVG/PNG 为渲染资源，不是连续动作或骨骼动画；前端动作仍需自己的轻量播放层。

### 复用路径：静态可用，创作时按需接服务

1. **默认体验**：按当前授权范围选取并适配现有素材，整理为版本固定的静态资源随插件交付，常用表情本地切换。不开后端也能显示、回应与使用已保存角色。
2. **基准组合**：需要换装/配色时，经 BenchGo 服务端的薄适配层调用已有渲染服务，复用目录与校验，导出后缓存为用户资产。不为播放动作维持网络调用。
3. **完全原创**：上传或图像工具创作，绑定自己的表情与动作映射，不套用基准几何、眼睛、挂点或装饰。不兼容的基准素材不强行拼贴。
4. **缺少资源**：先确认当前目录是否真的缺少，再用已配置图像能力补充；既有衣服可组合时不重新生成整只宠物。

不在当前任务中启动或改写参考服务。实际接入时使用显式配置的服务地址、版本和必要认证，连接由服务端管理，浏览器不接收密钥。服务不可达时保留静态资源/上传/已有角色，禁止回退成静默改形象。部署可复用已有服务；只有确有离线组合需求再评估打包渲染核心，不默认给每个客户端附加 Python 常驻进程。

基准渲染使用 780:560 画布，而 BenchGo 正式透明母版为 840×760，并有编辑器特征。复用要确认“完整基准角色作为个人外观”与“保持 BenchGo 默认品牌形态”的区别，不能直接换表情时顺便丢掉编辑器特征。先校验适配结果，保存快照；不修改参考项目真源，也不宣称所有素材天然无缝兼容。

保留原项目版权与资产使用说明，导入清单记录来源版本。本设计以用户授权的本项目复用为范围，不把来源素材自动宣布为公共领域或开放给第三方自由再分发。源码与接口已只读核实，未进行真实服务请求及组合运行验收。

## 10. 实施顺序与验收

### 第一阶段：可对话创作、会回应的应用内宠物

一次交付完整小闭环：默认无名字、主人/宠物两类档案的统一呈现、已适配的基准表情与装饰、上传与裁切、复用可用图像能力的聊天创作/换装/表情编辑、预览应用与恢复、共享角色组件、几种基础动作、真实事件映射。生成服务不可用时明确说明，不能因此阻塞默认角色和上传使用；但也不能将静态头像交付描述为已完成全部陪伴能力。

优先用用户消息与真实工作事件获得稳定反馈，再在现有回复契约适配时加入可选语义表达。不为该提示新开模型请求。基础动作与对话创作属于核心体验，不再整体推到远期。

验收故事：

- “我要一只机械水母”得到一个候选，应用后聊天中可见；同一角色在工作台与重载后保持一致。
- “换成机械水母的外观”仍是同一助手，名字、人格、记忆和进行中的任务保留；改名与人设修改走同一档案体系。
- “换黄色雨衣”保留角色身份；开始工作时能用新衣主图表现专注，不播放旧衣表情。
- “做一个开心表情”生成并应用后，“开心一下”复用已有素材，不重新生成。
- 普通聊天有节制地回应；长回复不反复触发动作，严肃内容不随机庆祝。
- 任务只有真实验收成功才播放完成；待确认与断线提示准确，动作不代替授权。
- 没有图像服务、缺少表情、保存冲突、生成取消和迟到结果均有明确降级，不覆盖当前有效配置。

### 第二阶段：轻量桌面陪伴

先验证宿主扩展能力，再交付同一宠物窗口的显示、拖动、回到聊天、隐藏恢复、前后台播放选择和多屏管理。验收是否挡点击、抢焦点、丢失窗口、重复播放或误停任务。

### 暂不承诺的扩展

只有用户真实需求和现有素材不足时，才评估多帧动作、自定义动作绑定与更多表达；不预排素材商城、养成、成长里程碑、骨骼编辑、自建复杂配饰系统、多宠物同时运行和完整历史库。

实现时运行对应配置、资源、状态映射和生命周期的定向验证。网页修改后执行 `npm run reload:plus`；本次仅文档评估，无须构建或视觉验收。

## 11. 平台参考的有效借鉴

| 参考方向 | 保留的启发 | BenchGo 的简化 |
| --- | --- | --- |
| Memoji、Mii | 可识别的个人角色，少量关键特征保持一致 | 用对话和图片修改，不做复杂滑杆编辑器 |
| Bitmoji、聊天表情 | 同一角色具有多种表达，形成熟悉感 | 已有完整表达资源优先复用，缺少时按需补充 |
| Peeps | 编辑结果即时可见，预览围绕角色 | 一个预览与应用动作，不复制独立工作室 |
| Discord | 个性化表达仍要保持身份与正文清晰 | 聊天只有一处主要动态角色 |
| 桌宠、虚拟角色 | 环境存在感与自然回应 | 动作库、透明轻窗口，复用原有聊天 |
| Tamagotchi、Pokémon | 熟悉动作与共同经历产生陪伴 | 保留角色连续性，不引入照料负担和养成数值 |

这些是设计范式参考，不是各平台最新版本的实测功能对照。效果应通过“用户能否创造自己喜欢的角色、角色回应是否自然、是否影响工作”判断，而不是设置页、动作数量或生成次数。
