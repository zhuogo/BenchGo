# 目标追踪现状与边界

2026-11-04 源码校对。Muse 的结构来自用户描述与截图，不作为已独立验证的实现事实。

## 已实现

- **结构化本体**：`runtime-store.mjs` 的 SQLite `assistant_goals` 表保存 ID、状态、版本和目标 payload，不以 Markdown 作为目标本体。
- **入口**：资源 → 工作区 → 任务 → 持续目标；`client/goals.jsx` 提供创建、列表、预算、暂停/恢复、停止和查看工单。
- **执行归属**：`scheduler.mjs`、`goal-ticket-creation.mjs` 将叶目标绑定工单，沿用 Router/Worker、授权、预算和验收机制；完成状态来自当前版本工单验收。
- **子目标**：已有子目标树和祖先预算，不限定一层。
- **创建与控制边界**：每个叶目标须提供已注册项目、原样 provider/model ID 和执行指令；`goal.requestId` 用于创建去重，不能把普通问答自动升级成持续目标。模型 `assistant_goals` 创建仍经过审批。暂停和停止分别有 `pausing`、`cancelling` 中间态，等待底层工单确认；不是界面点击后立即完成。
- **预算**：支持共享祖先 `requests`、已观测软限制 `tokens` 和 Unix 毫秒 `deadline`；费用 `cost`、旧 `scope` 不支持。调额要求当前版本，不清零累计量、不自动恢复执行；须通过预算恢复入口继续，原证据验收等待不重跑 Worker。
- **定时执行**：复用 DeepSeek Harness 原生 Schedule。`schedule-bridge.mjs` 只把官方定时消息转换为 Trigger，按来源会话、scheduleId 和 occurrence 去重，然后走工单执行与交付；不实现第二个 cron。

## 与长期追踪目标的差距（待实施）

当前是执行型目标，创建叶目标需要项目、模型与执行指令，不适合只记录“等待服务器 IP”等不立即执行的长期事项。

| 层次 | 当前缺口 | 后续复用方向 |
| --- | --- | --- |
| 系统记录 | 无独立的按日期目标进展账、简报和等待决策摘要 | 扩展既有目标服务，保持 ID 与版本权威；复用工单证据 |
| 工作区 | 无每目标说明书、成果目录与内部账本目录 | 目标记录持有受控目录引用；GOAL.md 只是笔记，不能替代目标记录 |
| 上下文投影 | 活跃目标未随每轮上下文注入；模型须主动查询 | 有界注入当前会话授权可见的活跃目标及待决策摘要 |
| 自动化归属 | Schedule 桥接未保存 goalId | 既有目标与官方 scheduleId 关联；Harness 管计时，目标管归属 |
| 展示 | 无独立“追踪/已完成”视图及摘要显隐 | 复用目标列表，不复制工单执行面板 |

追踪目标不自动授权执行。创建目标、绑定自动化、目标完成、停止自动化须分别按真实用户意图处理，不能因目标存在就启动无期限任务。外层可以展示“追踪/已完成”，内部可靠执行状态不必为了模仿截图而删除。

本轮只核对并记录这些缺口，未将规划冒充已实现，也未新增目标数据库、cron 或孤立占位模块。
