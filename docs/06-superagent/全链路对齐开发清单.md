# SuperAgent 全链路对齐开发清单

校对日期：2026-11-05。目标路线以[全链路架构](全链路架构.html)为准；本清单记录目标、P0 集成状态与后续开发，不通过修改目标来迁就现状。记忆直写按用户已完成的版本作为基线，不重复列为未实现功能。下方勾选表示相应交付门槛完成，代码存在或局部测试通过不单独勾选整条用户路径。

## 实施约束

复用 Ticket → Assignment → Run → Result → Delivery、官方 Harness 会话和现有持久 inbox/outbox，不新增执行系统、安装包或消息中间件。结果类型优先用现有 target、acceptance 和结果包表达，不要求先新增强制 schema；`blocked` / `review_wait` 是等待原因分类，不宣称当前 API 已有这些枚举。公开协议如有变动再同步工具、OpenAPI 与兼容策略。

停止、授权变化、预算、版本和未知效果的门禁优先于续做。不能因自动继续而重放不可逆动作。P0 先以桌面和飞书形成可用闭环，再逐渠道推广；基础场景通过前不宣称整条链打通。

## P0：先修复“有结果却卡住”的主闭环

- [ ] **按任务目标验收结果**：在 Router 验收规则和结果包说明中明确纯文本/新闻任务不要求 `artifactRefs` 或非空 checkpoint；加入“正文 + 来源/时间 + 工具证据”回归夹具。
- [ ] **验收失败自动续做**：把普通 `failed` 改成可分支处理。仍在原授权、预算和范围内时，生成 AI 修正指令，恢复原 Ticket / Assignment / Run / session 继续执行；保留 `instructionRevision`、预算、停止门和执行 fence。
- [ ] **阻塞等待可恢复**：只有缺用户信息、权限或范围决定时进入 `blocked`；提交时创建绑定原 Ticket、结果版本、问题和来源的 Attention，用户回复后恢复原单。内部证据或模型暂不可用使用 `review_wait`，不要求用户点“重新验收”。
- [ ] **消除固定失败/等待文案**：合法交付、返工说明和阻塞说明均由 Router 生成自然文本；模型不可用或结构非法时显示明确的系统状态，不伪装成 AI 报告。
- [ ] **给每个等待状态下一步**：主聊天、任务页和活动面板显示原因、当前状态与可执行动作（回答、继续、重试、停止）；不能只显示“待确认”或“证据未变化”。
- [ ] **桌面入口接入持久 inbox**：让官方 composer 进入现有持久 `send`，覆盖排队、去重、取消和重启恢复；清空模型上下文后仍应能按稳定主人/逻辑会话归属管理原有工单。
- [ ] **首轮 Worker 耗尽执行额度可恢复**：真实新闻 `real-no-files-01` 已失败；10 分钟 deadline 后不能只留 uncertain/open 且无状态告知。核实执行停止与未知效果后进入资源等待，提供显式补额度/继续或停止，不自动加额度；代码与定向覆盖已补齐，仍需另跑真实首轮无 Result 场景，保留首轮失败证据。
- [x] **独立工单短标题基础**：统一归一为最多 10 个 Unicode 字符，保持完整目标与验收条件，改名不递增任务要求版本；标题/任务管理定向 8/8。活摘要与语义查重不包含在本项。

## P1：补齐架构链路

- [ ] **外部私聊直达 Router**：一对一低噪声消息进入持久 Router 主会话；群聊、高噪声和系统事件才走 intake → Gate → Assessment。
- [ ] **工单活摘要、查重与跟进**：独立短标题基础已落；继续按目标、进展和卡点维护活摘要，新建前按标题+活摘要查在办/刚关工单，由 Router 判断语义重复、代码核实并合并，保留来源和授权边界。可信原始 Trigger 做唯一约束，取消关键词式跟进硬拒绝；不能只完成短标题或 requestId/Trigger 幂等便认定查重已对齐。
- [ ] **新闻证据保真**：保存 URL、来源标识、发布时间、抓取时间、多源关系和访问失败原因；缺一站不阻塞已有证据的交付。
- [ ] **交付后关联调整单**：原单保持 `completed`，用户追加反馈创建关联 adjustment Ticket，不 reopen 原单。
- [ ] **上下文与内置规则真源**：补齐 Router 十项开局包、每轮按需材料、辅助模型异步对齐总结和旁聊标题/摘要；Worker 只接任务包切片和原文指针；接入 `prompts/builtin-layer.md` 并纳入发布清单。
- [ ] **三角色模型及 Key Pool**：角色模型、工作模型、辅助模型分别配置与路由；按图落实密钥池职责。当前仅首选/备用模型队列，优先复用基础层凭据与供应商路由，不直接恢复旧 `keyPools` 字段或复制凭据库。
- [ ] **跨渠道提问与投递恢复**：补齐 Telegram/Discord/微信/WhatsApp 等来源关联与回答续做；区分确定未发送与发送未知，提供核实/重投入口。

## 第一批完成门槛

1. 有真实抓取记录的新闻任务，最终 6–10 条、领域覆盖和来源标记符合要求；无文件也能 completed，并在原聊天收到正文。
2. 首次给出 14 条或来源标记不足时，Router 告知原因，自动原单补查/修正，用户不用反复点“重新验收”。
3. 搜索失败但直抓成功：按证据与任务要求交付并说明渠道限制；全部联网失败：明确等待原因和恢复方式，不编造新闻。
4. 确需用户回答的问题有 Attention，回答绑定原单继续；内部核验故障有自动恢复状态，不让用户确认事实真伪。
5. 停止/撤权/预算不足/版本变化、重启、重复回调和通知失败不导致重复执行；未知外部效果先核实。
6. 桌面真实输入和后台完成均经过持久协议；主聊天自然回复、工单状态与原来源交付一致。

新闻测试固定来源正文、报道时间、抓取时间、错误和已知结论；真实抓取另验，不要求每日新闻相同，不锁定 AI 回复句式。网页实施后执行 `npm run reload:plus`，根 `npm run check` 不替代运行验收。

## 交付顺序

先完成 P0 的纯文本验收与失败/阻塞续做，再接 P1 的入口、去重、证据、上下文和规则真源，最后做 P2 的渠道扩展与真实场景验收。每项完成后同步《现状》《首版验收缺口》和对应专题文档，并记录“代码存在 / 定向测试 / 真实验收”三种状态。

本轮已取得 Router 真实供应商流式通过记录；新闻零文件首轮因执行额度耗尽后的等待/恢复缺口失败，正修复。14 条修正、Router/Worker 阻塞及真实桌面重启仍待场景验收，不能由流式或全量单测推定通过。未重跑用户历史工单，也不以新场景证明示例新闻真实。P0 完整闭环取得证据前不勾完上述路径。
