# 2026-11-05 晚：渠道关联与投递恢复

## Mandate（实现前固定）

1. Telegram、Discord、WhatsApp、微信沿用原始渠道标识；有平台回复标识时保存 `parentMessageId`。Telegram 的发送回执与入站回复标识使用相同命名空间。
2. Worker 与 Review 的 Attention 均保留原工单、原问题和来源。回复只能命中当前版本、同渠道/连接/聊天、原请求者的问题；微信等无平台引用能力的来源可用显式 Attention 编号回答，不猜最近工单。
3. 请求前已知失败和明确远端拒绝标记 `deliveryOutcome: not_sent`，允许带退避重试；网络超时、无回执及部分分片已发送标记 `unknown`，不得盲重发。
4. 未知投递通过已认证主人提交核实证据：确认送达保存原回执；确认未发送才回队列；仍未知保持等待。状态变更校验尝试次数，防止旧核实覆盖新发送。
5. 私聊直达 Router 必须复用持久 inbox 并保存来源、权限边界及原渠道回投。主会话现有工具默认桌面主人权限；未形成完整来源门禁前，不用 `engine.send(text)` 冒充安全直达。

## 实施范围

复用现有 Trigger / Attention / direct replies / outbox，不建第二队列，不改官方组件或定时服务。新增传输错误元数据和核实接口属增量协议；HTTP/MCP 接线与 OpenAPI 由主代理统一。

### 核实契约

`reconcileDirectReply(id, { attempts, outcome, evidence, receipt? })` 仅接受当前 `uncertain` 尝试；`outcome` 为 `sent / not_sent / unknown`。非空 `evidence` 留存审计；`sent` 必须附原始 `accepted + messageId` 回执；`not_sent` 等待 30 秒后重新领取；`unknown` 原地等待。已保存成功分片时不允许把整条核实为未发送并重投。宿主 `directReplyReconcile` 操作只允许已认证主人调用。存储本身不赋予调用者权限。

### 第18项边界

已与 engine 负责人核对：主会话将用户消息重写为 `desktop-owner`，工具注册捕获桌面权限且使用私人记忆。当前没有可复用的逐消息来源、权限和隐私上下文注入契约，无法以小改安全接入。保持渠道现有持久候选队列与原渠道回投；私聊直达主 Router 明确未完成，不以 `engine.send` 绕过边界。

## 验证方式

定向单元/集成夹具覆盖跨渠道编号/引用回复、错误分类、未知不重投、核实后恢复、重启持久性和来源隔离。不开真实渠道发送、不调用模型；这些结果仅称受控验证，不称真实渠道验收。
