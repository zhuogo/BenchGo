# BenchGo 设备与中继设计

状态：方案基线，待按根目录 `task/设备与中继重构.md` 实施。

本文是 BenchGo 设备连接、登录入口、自托管中继和后续官方中继池的唯一产品设计基线。`deepseek-harness/` 与 `reference/` 不属于实现范围。

## 实施状态（2026-10-24）

- 产品对外只有两个安装包。`benchgo` 是完整工作台，可以连接外部中继，本身不安装中继服务。`benchgo-relay` 是独立中继服务器。不再发布 `@benchgo/server`。
- 已完成路线和 UI 单测、Link 全量测试与网页重建；公网域名/IP、ACME、端口冲突、SSH 一键安装和 NPM 正式发布仍需真实环境验收。
- 工作台包只带工作台安装器，中继包只带 relay runtime。正式发布前仍需 GitHub Actions 签名和发布验收。

## 1. 定位与边界

```text
BenchGo       工作台：项目、会话、模型、任务和插件状态留在目标主机。
设备          一台可访问的 BenchGo 工作台，可以是本机、电脑、手机或云服务器。
设备中心      管理设备、连接路线、配对、部署、撤销和诊断。
中继          直连失败时的备用传输层，只转发已授权的 BenchGo 流量。
launch-token  首次进入公网工作台的短时票据，使用后换成 HttpOnly 会话。
```

目标是“地址 + token 即可打开”，用户不需要理解 Link、代理、owner、鉴权探针或中继协议。

### 已确认的登录决策

现有 `launch-token` 是 BenchGo 唯一默认的云端登录方式。任何公网域名或公网 IP 入口都必须优先支持 `?token=xxxxx`，成功后换发会话并清理 URL；不再新增或要求用户配置第二套云端访问密钥。后续若需要企业级额外防护，只能作为独立高级部署能力，不能改变默认入口或重新引入 `cloud-access` 链路。

中继不承担工作台、模型、项目、账号或 owner 管理职责；中继运营者只应是用户信任的基础设施管理员。

项目公开名称统一为 BenchGo，后续 GitHub 仓库使用 `BenchGo/benchgo`（旧地址保留跳转）。统一 CLI 覆盖工作台和中继，但两者仍使用独立运行包和独立生命周期。

## 2. 连接策略

设备保存多条候选路线，打开时自动选择：

```text
局域网直连 → 公网直连 → 中继池主中继 → 备用中继 2 → 备用中继 3 → 诊断
```

- 目标本身有公网地址且直连可用时，不经过中继。
- 两台设备都没有可用入站路径时，双方主动接入中继。
- 普通用户不手动选择路线；高级用户可以查看实际路线和重试。
- 连接成功后显示“局域网直连”“公网直连”或“经中继”。
- 证书错误、身份不匹配、授权拒绝不得静默降级到下一条路线。
- 连接失败不停止目标主机任务，不重放已提交的写请求。

### 中继池故障转移

中继池由有序节点列表组成，每个设备或设备组可以指定主中继和备用中继：

```text
Relay 1（主） → Relay 2 → Relay 3
```

- 直连全部失败后，优先尝试 Relay 1。
- Relay 1 连接失败、超时、离线或健康检查失败时，进入短暂冷却并尝试 Relay 2。
- Relay 2 同样失败时继续向后切换，直到成功或全部失败。
- 成功节点记录为最近可用路线，但不覆盖用户配置的优先级。
- 主中继恢复后，新连接回到主中继；正在运行的会话不强制迁移。
- 同一连接请求只允许有限次尝试，避免中继循环和重复写入。
- 中继池只能提高可用性，不能承诺网络、主机或公网服务永远可用。

## 3. 设备中心界面

顶部保留三个主标签：

```text
设备 | 连接 | 中继
```

### 设备

- 本机排在设备列表第一项，与其他设备使用相同卡片和打开流程。
- 已添加设备及当前路线、最近错误和最后连接时间。
- 添加设备：连接已有 BenchGo，或通过 SSH 在服务器安装 BenchGo。
- 设备卡片不显示 token、SSH 密钥或中继密钥。

### 连接

- 单独承载本机连接设置、允许其他设备连接、批准申请和撤销设备。
- 不把连接配置插入设备列表，避免设备页被本机设置撑长。

### 中继

- 我的中继池，首版一个自托管节点即为单节点池。
- 添加中继：SSH 一键安装，或复制手动安装命令。
- 主中继、备用中继、优先级、健康状态和最近错误。
- 域名/IP、证书、外部连通性、启停、重启、卸载和密钥轮换。
- 用户平时不需要打开中继页；设备页自动使用已配置中继。

## 4. 用户路径

### 4.1 连接已有设备

```text
设备中心 → 添加设备 → 扫码 / 粘贴连接信息 / 输入地址
→ 目标设备批准 → 保存设备身份和路线 → 真实工作台验证 → 打开
```

配对码短时、单次、限流。配对完成后保存设备独立凭据，正常使用不重复输入 owner 登录信息。

### 4.2 在服务器安装 BenchGo

```text
设备中心 → 添加设备 → 在服务器安装 BenchGo
→ SSH 指纹确认 → 输入认证信息 → 安装并启动
→ 生成入口 token → 验证真实工作台 → 自动加入设备列表
```

SSH 命令成功不等于部署成功，必须完成真实页面、API 和必要 Gateway 验证。失败显示阶段、日志和重试动作；移除设备连接不隐式卸载服务器服务。

### 4.3 部署自有中继

```text
设备中心 → 中继 → 添加中继 → SSH 一键安装 / 手动安装
→ 检测公网地址、端口和证书 → 启动中继
→ 目标主机建立出站连接 → 真实设备完成中继工作台验证
```

中继部署成功必须以真实设备访问工作台为准，不能只依据 SSH 或服务进程状态。

部署向导提供“IP SSL”和“域名 SSL”两种模式。IP 模式要求公网 80 可达；域名模式在部署前校验 A/AAAA 解析指向目标公网 IP，再进入 ACME 验证。已有中继服务先展示状态并复用，禁止重复安装或覆盖非 BenchGo 服务。

## 5. 默认登录入口

移除独立“云端访问密钥”链路，统一使用已有 owner launch-token：

```text
https://benchgo.example.com/?token=xxxxx
https://公网IP:48721/?token=xxxxx
```

```text
短时 token → 服务端校验 → HttpOnly / Secure / SameSite 会话
→ 清理地址栏 token → 进入工作台
```

约束：

- token 一次性或短时有效，不写日志、不返回 API、不进入设备记录。
- owner 会话只负责当前工作台和 owner 管理入口。
- 设备凭据只负责已批准工作台，不能伪装 owner。
- 中继凭据只负责设备接入和授权转发，不能替代设备凭据。
- 删除 `cloud-access` 模块、配置、探针、UI、OpenAPI 字段、测试和文档，不保留兼容分支；该删除必须在第一阶段完成，不能留作后续清理。

## 6. 中继架构

```text
私网设备 A ──TLS 出站连接──┐
                            ├─ Relay Node
私网设备 B ──TLS 出站连接──┘
                            │
                      已授权工作台流量
```

中继只负责：

- 接受设备主动建立的出站连接。
- 验证设备身份、目标设备和授权关系。
- 转发白名单内的工作台 HTTP、事件流、Gateway 和必要 WebSocket。
- 处理心跳、断线重连、背压、超限、健康状态和撤销后的连接清理。

中继禁止：

- 任意 TCP、SOCKS 或通用 HTTP 代理。
- 访问 owner 管理 API、SSH、文件系统或未登记目标。
- 保存模型密钥、项目、会话或长期工作台 Cookie。
- 把中继密钥当作设备身份。

首版 TLS 在用户控制的中继终止，因此中继运营者可以看到转发内容和元数据；不宣称端到端加密。

## 7. 中继池模型

首版不建设公共控制面：用户自托管的 Relay Node 是一个单节点中继池。协议和数据模型预留多节点：

```text
Relay Pool
  ├─ primary: Relay 1
  ├─ fallback: Relay 2
  └─ fallback: Relay 3
```

设备保存中继 ID、优先级和授权引用，不把节点地址当成设备身份。节点更换、停用或密钥轮换必须重新验证，不得静默导流。

后续官方中继池复用同一协议，提供自动选择、区域选择和自托管选择；当前不依赖官网即可完成自部署。

## 8. 地址、端口与证书

### 8.1 端口

不要求用户占用或释放 `80`、`443`、`4443`、`40` 等常见端口，也不停止宝塔、Nginx、Apache、Caddy 或其他已有服务。

- BenchGo 和 Relay 默认选择空闲高位端口。
- 部署前检测冲突，展示实际端口和防火墙要求。
- 已有反向代理时生成可复制配置片段，只接入用户指定路径。
- 不自动改写站点、不自动改防火墙、不覆盖已有证书。
- 标准端口被占用时优先复用已有反代，不抢占端口。

### 8.2 域名和公网 IP

域名是推荐公网方案；服务管理器负责 DNS、端口、证书和外部真实访问检查。公网 IP 可使用高位端口直接连接；有正式证书时优先 HTTPS。

### 8.3 HTTP 兼容模式

局域网允许 HTTP 或自签名证书。公网 HTTP 仅作为明确确认的不安全兼容模式，首次使用必须显示风险；不能把公网明文连接默认为安全连接。

原生客户端可使用自签名证书加 SPKI 指纹信任，但普通浏览器不能假定具备相同能力。


## 10. 数据、权限和诊断

设备记录保存名称、稳定设备 ID、路线、证书指纹、设备凭据安全引用、状态和最近错误。中继记录保存中继身份、接入设备、授权关系、心跳和短期路由状态。

设备、主机和中继分别支持撤销；撤销立即关闭活动会话或隧道。凭据不放在 URL、日志或不安全浏览器存储中。SSH 密码和私钥只在部署操作内存中使用。

普通用户看到动作导向的状态：

```text
正在连接 → 正在尝试中继 → 已通过中继连接
设备在当前网络不可达 → 检查目标设备是否在线
直连和中继都不可用 → 检查中继状态或重新配对
```

高级详情才显示 DNS、端口、TLS、指纹、Gateway、WebSocket 和服务日志。在线状态必须区分设备在线、中继在线、路线可达和工作台可用。

## 13. 验收基线

- 域名或 IP 加 token 能直接进入工作台，地址栏 token 被清理。
- 局域网可用时不经过中继；公网设备可达时不经过中继。
- 直连失败后按优先级自动尝试中继 1、2、3。
- 主中继恢复后新连接自动回主，不强制迁移活动会话。
- 中继不获得 owner 权限，设备撤销立即断开连接。
- 端口被宝塔等服务占用时可选择空闲端口或复用反代，不抢占、不停服务。
- SSH 部署完成真实工作台验证，失败可恢复。
- GitHub 安装脚本、NPM 包、手动安装和 SSH 安装使用同一服务协议。
- 未经过真实服务器、浏览器和移动网络验收的能力，不标记为已完成。

### 自有中继双证书模式（2026-10-25）
部署向导支持 IP 或域名二选一。域名模式在 SSH 部署前解析 A/AAAA 并要求至少一条记录匹配目标公网 IP；证书仍由 Certbot/ACME HTTP-01 webroot 签发。部署脚本只接管带 BenchGo 标记的目录和 systemd 单元，检测到外部服务或配置冲突即停止，不覆盖现有反向代理。

### 域名模式 HTTP-01 端口复用修正（2026-10-25）
域名 SSL 默认使用现有站点的 webroot，不启动独占 80 的 challenge 服务；部署前检查 webroot 存在、可写，并通过域名 Host 请求验证 `/.well-known/acme-challenge/` 可达。只有 IP SSL 默认使用 standalone；用户可显式选择 webroot。该检查不修改宝塔/Nginx/Apache 配置，验证失败即停止并给出站点根目录提示。
域名 webroot 采用“显式路径优先、有限候选自动探测、challenge 公网回读确认”的兼容策略，覆盖常见 Nginx/Apache/Caddy/宝塔目录；不自动修改未知 Web 服务配置，也不停止占用 80 的服务。
域名一键部署不依赖预装 Web 服务：检测到现有 Web 服务时复用其验证入口；未检测到 Nginx、Apache、Caddy 等服务时，若 80 端口可用则由 BenchGo 创建受归属保护的临时/续期 challenge 服务。前端只展示 IP SSL 或域名 SSL，不暴露实现组件名称。
中继池列表在添加成功后立即刷新，节点支持编辑地址、启用/停用、设为主中继和删除；删除最后一个节点时引导停用，避免产生空配置。密钥仍由服务端保存，列表和编辑操作不回显密钥。
